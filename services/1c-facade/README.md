# MCP-фасад для 1С

Один MCP-сервер вместо зоопарка: шесть глаголов наружу, маршрутизация,
резолвер имён и нормализация ответов внутри.

Статус: рабочий. Реестр, резолвер, карта здоровья, шесть глаголов,
нормализация, MCP-сервер и чекер правил за `check`.

Этот файл объясняет **почему** так устроено. Что делать в конкретной
ситуации — [`RUNBOOK.md`](RUNBOOK.md): карта парка, обычные операции,
расшифровка состояний бэкенда, типовые поломки.

## Запуск

```bash
cp services/1c-facade/registry.example.json services/1c-facade/facade-registry.json
# прописать проекты и монтирования выгрузок в docker-compose.yml
docker compose -f services/1c-facade/docker-compose.yml up -d --build
```

В целевом проекте — одна запись, **одинаковая во всех проектах**:

```json
{ "mcpServers": { "1c-facade": { "type": "http", "url": "http://127.0.0.1:8770/mcp" } } }
```

**Сервис живёт вне инсталляционной нагрузки — в `services/`, а не в
`overlays/1c/tools/`.** Инсталлятор копирует `tools/*` в каждый проект, а фасад
по смыслу машинный: он держит реестр всех проектов, адреса бэкендов и имена
контейнеров. Возить такое из проекта в проект незачем — он один на хост.
Чекер правил, наоборот, остался в `tools/`: он проверяет код конкретного
проекта и должен ехать с правилами, чтобы работать в pre-commit без фасада.

Зависимостей нет вообще — и фасад, и чекер на стандартной библиотеке, поэтому в
образе нет шага `pip install`, а пересборка занимает секунды. Сервер написан на
`http.server` и `json` по той же причине: инструмент, начинающийся с дерева
зависимостей, не включают.

Запуск прямо на хосте тоже работает — тогда пути и адреса в реестре обычные:

```bash
FACADE_REGISTRY=/путь/facade-registry.json python server.py --port 8770
```

**Поверхность — 2857 символов схем против 72 100 у восьми серверов, 4%.**
Но экономия тут побочный эффект: исчезают не столько токены, сколько сам выбор
бэкенда, который раньше делала модель по похожим описаниям.

## Зачем

В 1С-контуре несколько MCP-серверов с пересекающимися именами инструментов
(`codesearch` / `search_code` / `trace_call_chain` / `get_method_call_hierarchy`),
но с разной зоной компетенции. Пока выбор делает модель по тексту доктрины, она
регулярно уходит не туда: описания похожи, а разница видна только по качеству
ответа. Фасад переносит выбор из промпта в код.

Второе, ради чего он существует: сейчас «объекта нет», «индекс протух» и
«сервер выключен» дают одинаково пустой ответ. Блок `coverage` их разводит.

## Девять глаголов и проброс

```
find(query, project, kind=any|routine|metadata|form|text, exact, limit)
describe(id, project, sections)
calls(id, project, direction=callers|callees, depth)
usages(id, project, where=metadata|code|both)
check(project, scope=staged|path|diff)
status(project, reindex)
docs(query, scope=platform|its|any, version)        -- серверы платформы
lint(code | path + project, mode=syntax|check|review)
template(query | id)
```

Первые шесть работают над конфигурацией проекта, последние три — над
серверами платформы (документация, ИТС, синтакс-анализатор, проверка кода
Напарником, шаблоны), которые ни к одной конфигурации не привязаны.

**Правило проектирования: глагол там, где есть выбор между дублирующими
бэкендами; сквозной проброс там, где инструмент единственный.** Проброшенные
инструменты публикуются под именем `<бэкенд>_<инструмент>`
(`code_verify_xml`, `codecheck_ask_1c_ai`): API Claude принимает в имени
инструмента только `[a-zA-Z0-9_-]`, так что точка из проекта 0.2 не годится.
Схема берётся у бэкенда и кэшируется; бэкенд, лежавший в момент листинга,
просто отсутствует в нём — следующий `tools/list` попробует снова. Ответ
проброса не нормализуется, у проектных бэкендов в схему добавлен аргумент
`project`. Что публикуется — решают данные: списки `expose` в реестре.

`resolve` наружу не вынесен намеренно: резолвит каждый глагол сам, а
неоднозначность видна в `coverage.ambiguous`. Иначе вызывающая сторона обязана
помнить двухшаговый протокол — ровно то, от чего уходим.

## Маршрутизация — из замеров, не из вкуса

Замер на конфигурации в 446 модулей, эталон — grep по исходникам.

| Задача | Куда | Почему |
| --- | --- | --- |
| граф вызовов | `graph_metadata` | 8 из 8 против 2 из 8, и у второго ложный вызывающий |
| метод по имени | **резолвер**, `code_metadata` дополняет телом | у бэкенда есть провалы: на УЛК он не нашёл `ПолучитьЗначениеНастройки`, найдя соседей |
| объект метаданных | `code_metadata` | 0,1 с против 7,1 с |
| досье объекта | оба, слияние | досье подробнее, `code` добавляет типы реквизитов |
| использования объекта | оба, слияние | отвечают на разные вопросы: ссылки объект→объект против реквизитов с типом |
| использования **в коде** | grep | эталон 50 файлов, ни один индекс их не даёт |
| поиск по описанию | оба, союз | пересечение выдач 3%, союз почти вдвое полнее |
| форма по элементам и заголовкам | `code_metadata` (`search_forms`) | другого индекса форм нет |
| раскладка формы, структура модуля | `code_metadata` | `inspect_form_layout` / `get_module_structure`, у графа этого нет |
| граф вызовов без графового индекса | `code_metadata`, **фолбэк** | только когда граф не объявлен или не отвечает; `coverage.degraded` и пометка, что ответ слабее |

**Веер избирателен.** На поиске по описанию он почти удваивает полноту
бесплатно по времени — запросы идут параллельно (с 0.2 — действительно: до этого
два вызова шли подряд, а диспетчер ещё и сериализовал все вызовы фасада
глобальным локом), а выдачи почти не пересекаются. Покрытие параллельных
вызовов пишется в порядке запроса, поэтому один и тот же вопрос даёт один и тот
же блок `coverage`.

**`docs` не может опираться на пустую выдачу.** Поиск по документации
ранжирует без порога и на бессмысленный запрос отвечает статьёй про
`WebЦвета` — «пусто» от него не дождаться. Поэтому запрос вида имени
(`ТаблицаЗначений.Найти`) идёт в точный `docinfo`, который честно говорит «не
найдено», и только тогда в поиск; ответ поиска несёт в `coverage` пометку об
отсутствии порога. `version` уводит запрос в документацию конкретной версии,
`scope=its` — в базу ИТС, `any` — в оба корпуса параллельно.

**`lint` не смешивает режимы.** `syntax` — анализатор за доли секунды с
диагностиками по строкам (0-based ответ сервера переводится в 1-based);
`check` и `review` идут через модель Напарника и занимают десятки секунд.
Путь модуля читается из выгрузки проекта и не может выйти за её пределы.

**`describe` выбирает маршрут по `id`.** `Справочники.X.Форма.Y` — раскладка
формы и структура её модуля; путь `…/Module.bsl` или голое имя общего модуля —
процедуры модуля со строками и директивами; остальное — досье объекта, а
`sections: ["modules"]` / `["form"]` добавляют к нему модули и раскладку.
`get_module_structure` принимает только абсолютный путь внутри контейнера
бэкенда, поэтому корень выгрузки — поле `code_root` бэкенда в реестре
(по умолчанию `/app/code`). Раскладку формы бэкенд сейчас отдаёт только
деревом элементов: реквизиты, команды и обработчики формы пусты у всех
проверенных баз — парсер их понимает, но на живом ответе они не проверены.
На графе вызовов союз добавил бы известную ложную запись, на поиске метаданных —
семидесятикратную просадку ради ничего.

**`find(kind=routine)` переведён на резолвер после боевого прогона.** Символьный
индекс резолвера полон по построению — в нём каждое объявление выгрузки, — а
функцию бэкенда пришлось ловить на конкретном промахе. Бэкенд по-прежнему
опрашивается, он несёт тело метода, и записи сливаются по полям: находка,
которой нет у одного, доезжает через другого. Побочный эффект: глагол работает и
у проекта без бэкендов — по базе ERP это 4 находки за 0,19 с.

`check` в эту таблицу не попадает: он идёт не в бэкенд, а во внешний CLI из
`FACADE_CHECK_CMD` — `tools/rules-check`, проверяющий исходники правилами
оверлея. Реализация живёт там, а не здесь, намеренно: фасад знает про порты и
контейнеры конкретной машины, а чекер ездит вместе с правилами и должен
ставиться отдельно. Зависимость односторонняя — чекер про фасад не знает.

```bash
export FACADE_CHECK_CMD="python /путь/rules-check/rules_check.py"
```

## Несколько проектов

Один фасад обслуживает все конфигурации хоста. Подключение к сетям бэкендов
(`networks:` в compose) даёт адресацию по имени контейнера и внутреннему порту —
проброс на хост не нужен, и не важно, проброшен ли он вообще.

Боевое подключение (Project_BL) заменило **шесть** серверов одним: 96
инструментов и 112 227 символов схем против 6 и 2 857 — **в 39 раз меньше**.
Остальные семь записей в `.mcp.json` остались: справочные и корпусные серверы
фасад не покрывает и не должен.

⚠ **Имена проектов берутся из `Configuration.xml` выгрузки, а не из имён
контейнеров: имена контейнеров врут.** Инвентаризация парка дала вот что.

| было | стало | что индексирует | версия | модулей |
| --- | --- | --- | --- | --- |
| `project_bl_*` | `ulk_*` | **УправлениеЛизингом** — расширение вендора | 2.5.22 | 343 |
| `erp_bl_*` | `bl_*` | **БалтийскийЛизинг** — основное своё | 2.5.22 | 446 |
| `project_bki_*` | `bki_*` | **КонтурБКИ** — обмен с НБКИ | 1.0.0 | 40 |
| — | — | **УправлениеПредприятием** — база, которую расширяют все три | 2.5.22.166 | 25 092 |

Серверы с «BL» в имени индексировали УЛК, а настоящий БалтийскийЛизинг жил под
именем `erp_bl`. Проверяется мгновенно: `ПолучитьЗначениеНастройки`
существует в обоих расширениях и это **разные методы** —
`лиз_НастройкиУЛКПовтИсп` (31 вызывающий) против
`БЛ_ОбщегоНазначенияВызовСервера` (1). Пока оба лежали под одним именем, любой
ответ про «настройки BL» был про УЛК.

Контейнеры переименованы по `Configuration.xml`, реестр приведён в
соответствие. Что **не** тронуто и почему: имена томов держат данные, а
`PROJECT_NAME` партиционирует граф в neo4j — их смена означала бы переиндексацию
за деньги. Расхождение осталось только там, где оно безвредно и задокументировано
в компоузах.

Старые имена (`project_bl`) в алиасы намеренно **не** вынесены: пусть вызов с
ними падает со списком известных, а не резолвится молча не туда.

Попутно: `Project_BL/src_bl` и `1c-config-dumps/ERP_BL` совпадают байт-в-байт
(446 из 446) — это одна сборка в двух копиях, поэтому один проект, а не два.
Две копии базы (`erp_crc` и `dumps/ERP`) расходятся в 82 файлах из 121 648 —
это уже разные сборки, и какая из них актуальна, решать владельцу.

**Проект без бэкендов — рабочий.** У базы ERP нет ни одного MCP-сервера, но
резолвер и индекс ссылок строятся прямо из выгрузки, поэтому канонизация имён и
`usages(where=code)` по ней работают, а `calls` и `describe` честно сообщают,
что бэкенда нет. Это и есть место, где можно спросить «что расширение
переопределяет в базе» — раньше спросить было негде.

⚠ Цена оказалась не там, где ожидалось. Индексы сохраняются в томе, но замер
рестарта показал: `bki` 0 с, `bl` 8 с, `ulk` 6 с — и **`erp` 531 с**. Узкое
место не разбор, а перехеширование 121 648 файлов через bind-mount: оно платится
на каждом старте, даже когда не изменилось ничего. Хранения индекса тут
недостаточно.

Поэтому у проекта есть флаг **`frozen`**: выгрузка объявлена снимком, индекс
строится один раз и дальше открывается без пересканирования. **531 с → 1 с.**

Это констатация факта, а не оптимизация. В работе одновременно одно расширение;
остальные выгрузки и база лежат неизменными, и перепроверять их на каждом старте
незачем. Поэтому `frozen` стоит у всех, кроме активного — старт всего парка
занимает 8 с вместо девяти минут:

```
bki 0 с   bl 7 с (активный, пересканируется)   erp 1 с   ulk 0 с
```

Сменилось активное расширение — переставить флаг. Заменили выгрузку-снимок на
диске — `status(project=…, reindex=true)`, реестр править не нужно и
перезапускать нечего. Без этого «заморожено» было бы ловушкой.

## Резолвер имён

Существует из-за измеренного дефекта: `code_metadata` матчит процедуру по голому
имени, поэтому `ОтправкаПочты` возвращает вызывающих *каждой* одноимённой
процедуры, а квалифицированная форма не возвращает ничего. Слить записи двух
бэкендов нельзя, пока канонический id не выбран **до** первого вызова.

Индекс строится из выгрузки конфигурации, а не из бэкенда: он обязан отвечать,
когда бэкенд лежит. SQLite, только стандартная библиотека, инкрементально по
SHA-256. Полная конфигурация в 446 модулей — 4123 символа за 0,4 с.

Неоднозначность не проглатывается: при нескольких кандидатах предпочитается
экспортный, а остальные возвращаются в `coverage.ambiguous`. Когда выбрать
нельзя — глагол честно отвечает списком кандидатов.

⚠ **Квалификация должна доезжать до бэкенда, а не только до конверта.** Первая
версия слала графу голое имя, а канон подставляла в `rel.to` уже в ответе. На
Project_BL это дало худший из возможных исходов: граф разрешил
`ПолучитьЗначениеНастройки` в одноимённый метод модуля формы, резолвер — в
экспортный из общего модуля, и конверт уверенно приписал вызывающих одного
методу другого. Теперь владелец едет параметром `object_name`, а эхо бэкенда
сверяется с каноном: расходятся — ответ помечается `degraded` с обоими именами.
Молча переклеивать чужой ответ на своё имя — так неверные данные выглядят
верными.

⚠ Экспортность определяется балансом скобок, а не окном фиксированной длины:
окна, достаточного для многострочного списка параметров, хватает и на то, чтобы
дотянуться до `Экспорт` следующей процедуры. На реальном корпусе это ровно один
метод из 242 — и однострочная регулярка его теряет.

## Индекс ссылок

Резолвер читает всю выгрузку, когда строит таблицу символов, — поэтому заодно
индексирует **ссылки на объекты метаданных в коде** (`Справочники.X`,
`СправочникСсылка.X`, `ДокументОбъект.X` и прочие приставки доступа). Ни один
бэкенд их не отдаёт: оба работают на уровне метаданных.

Мерилось на живом контейнере, ERP_BL, 446 модулей:

| | обход дерева | индекс |
| --- | --- | --- |
| `usages(where=code)` | 7,2 с **на каждый вызов** | 0,006 с |

Обход шёл по bind-mount, и это была не разовая цена, а постоянная. Заодно
выросла полнота: обход останавливался на первом совпадении в файле, индекс даёт
построчно.

⚠ Ссылки индексируются по сырому тексту, без вырезания строк и комментариев:
упоминание объекта в тексте запроса или в закомментированном коде попадёт в
выдачу. Для «где используется» это скорее плюс, но `src.tier` у таких записей
не зря `grep`, а не `indexed`.

## Прогрев

Индекс строится лениво при первом обращении, а по bind-mount это секунды, пока
вызывающий ждёт: холодный `calls` на ERP_BL стоил 8,7 с при 0,02 с в тёплом.
Поэтому сервер собирает индексы всех проектов реестра фоновым потоком на старте.
`status` отвечает и без индекса, так что сервер полезен сразу; проект, чья
выгрузка не смонтирована, сообщает об этом в лог и не мешает остальным.

## Карта здоровья и жизненный цикл

`status()` показывает состояние парка: отвечает ли бэкенд, поднят ли контейнер,
какого возраста индекс. Состояния `up` / `cold` / `down` / `unknown` различимы —
`cold` означает «контейнер есть, но остановлен», а не «объекта нет».

Отдельно отмечается **`indexing`**: бэкенд отвечает, но индекс ещё строится.
Пустая выдача в этот момент означает «ещё нет», а не «нет такого» — и без
пометки эти два случая неразличимы. Всплыло сразу после пересоздания контейнера
УЛК: `find` вернул ноль, и по конверту нельзя было понять, почему.

Индекс бэкенда лежит в именованном томе, поэтому рестарт контейнера —
инкрементальный догон, а не пересборка. Фасад умеет поднимать бэкенд по
обращению, но делает это **только** там, где в реестре стоит `cold_ok`: будить
чужое — побочный эффект, и согласие на него фиксируется данными, а не кодом.
`evict()` по LRU по умолчанию работает вхолостую и требует явного запроса.

Демон достаётся тремя способами, по убыванию предпочтения: сокет
`/var/run/docker.sock` (фасад в контейнере), бинарь `docker` (фасад на хосте),
никак. В последнем случае состояние честно `unknown` — это не то же самое, что
«контейнера нет».

⚠ **Монтирование сокета равносильно root на хосте.** В `docker-compose.yml` оно
закомментировано намеренно. Без него фасад полностью рабочий: он просто не
запускает остановленные бэкенды, а сообщает, что не может.

Клиент Engine API написан поверх `http.client` и unix-сокета — ставить в образ
docker CLI ради трёх HTTP-запросов не потребовалось.

## Реестр

Одна запись на проект: путь к выгрузке, адреса бэкендов, имена контейнеров,
алиасы. Именно она заменяет десяток блоков в проектном `.mcp.json` — целевой
проект подключает один фасад, адреса знает фасад. Она же убирает угадывание
хоста по соседству.

Шаблон — `registry.example.json`; рабочий файл `facade-registry.json` или путь
в `FACADE_REGISTRY`, оба вне репозитория.

Кроме проектов в реестре две секции 0.2:

- `expose` — `{"code": ["verify_xml", ...]}`: инструменты, публикуемые
  пробросом у каждого бэкенда этого вида; бэкенд может задать свой список
  (пустой — выключить).
- `shared` — серверы платформы (`docs`, `syntax`, `codecheck`, `templates`):
  адрес, таймаут и свой `expose`. Проектом они не являются и по имени не
  адресуются; `status` без проекта показывает их вместе с парком.

У бэкенда два необязательных поля 0.2: `timeout` — потолок одного вызова в
секундах (по умолчанию 120; обход графа на полной ERP законно идёт десятки
секунд, поиск по коду — десятые доли) и `code_root` — где бэкенд монтирует
выгрузку.

## Нормализованная запись

Всё, что отдают бэкенды, — сущность плюс необязательное ребро:

```
id      канонический квалификатор (от резолвера, не из эха бэкенда)
kind    metadata | module | routine | attribute | form | element | command | snippet
name, owner
loc     path (репо-относительный) + line/end
sig     сигнатура
rel     type (calls | called_by | references | referenced_by | typed_as | overrides
              | child_of — элемент формы внутри родителя)
        + to + depth + via
text    тело либо фрагмент
src     backend, tool, tier (indexed | live | grep), score
```

`src.tier` — не украшение: когда ответ пришёл из grep или из живого XML-скана, а
не из индекса, вызывающая сторона обязана это видеть.

Дубли сливаются **по полям**, а не выбором победителя: бэкенды дополняют друг
друга именно на уровне полей — один несёт расположение в файле, другой сигнатуру.

## Парсеры и защита от смены формата

`graph_metadata` отвечает форматированным текстом. Текст машинно-сгенерирован по
устойчивому шаблону, поэтому разбор — регуляркой: детерминированно, пиннится
фикстурами, стоит ноль.

Защита при обновлении образа — **детектор дрейфа**: каждый парсер сверяет число,
объявленное сервером в собственной шапке, с числом разобранных записей; для
досье — посекционно. Разошлось — гейт красный, и видно, какая секция уехала.

Отказ бэкенда (`{"status":"error","error":"Module not found: …"}`) — не дрейф:
это определённый ответ про объект, парсер отдаёт его как `not_found` с текстом
отказа. Ответ из запасного слоя, пока бэкенд строит индекс
(`indexing_status: in_progress`), тоже помечается: пустота тогда значит «ещё
нет», а не «нет такого».

## Конвейер и гейты

```
python capture.py        # сырые ответы -> fixtures.local/ (вне репозитория)
python anonymise.py      # обезличенные -> fixtures/
python test_parsers.py   # парсеры: инварианты + снапшот
python test_facade.py    # резолвер, реестр, глаголы (на реплее фикстур)
python test_server.py    # протокол сквозь настоящий сокет
```

`capture.py` берёт адреса из `FACADE_CODE_URL` / `FACADE_GRAPH_URL` — машинных
адресов в дистрибутиве нет. `--only a,b` снимает только названные случаи: новый
парсер не должен заставлять перебазировать старые фикстуры по тому, что лежит в
корпусе сегодня.

`anonymise.py` обязателен: сырые ответы содержат префиксы объектов заказчика,
имя конфигурации и внутренние хосты в телах процедур. Отображение меняет
идентификаторы и вырезает тела, но не формат — а тестируется именно он; все
счётчики сохраняются, поэтому инварианты остаются осмысленными.

Гейты не требуют живых серверов: глаголы гоняются на клиенте-реплеере, резолвер —
на синтетической выгрузке в `fixtures/source/`. Корпус маленький, но
воспроизводит дефект, на котором держится вся конструкция: две процедуры
`ОтправкаПочты`, одна экспортная.

Расхождение «8 против 2» между бэкендами зафиксировано **как инвариант**. Если
поставщик когда-нибудь починит свой обход графа, гейт упадёт — и это правильно:
маршрутизацию придётся пересматривать, а не тихо жить со старой таблицей.

`test_server.py` поднимает сервер на эфемерном порту и говорит с ним тем же
клиентом, каким фасад говорит с бэкендами, — протокол проверяется по-настоящему,
фиктивны только бэкенды. Именно этот гейт поймал то, что не видно из
однопоточных тестов: соединение SQLite не переживает смену потока, а
`ThreadingHTTPServer` обслуживает каждый запрос в новом.

## Чего не хватает

- **Правила, требующие навигации.** Механически разрешимые уже проверяются
  (`tools/rules-check`); класс «нет ли уже такого в БСП», «не сломает ли
  переопределение базу» должен идти через глаголы фасада, а не через
  регулярку.
- **Офлайновая карта синонимов** «бизнес-термин → объект» для резолвера.
  Строится заранее и кэшируется. В тракте запроса внешних моделей быть не
  должно: недетерминированный шаг обесценивает гейт на фикстурах.
