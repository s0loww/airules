# Фасад 0.2 — единая точка подключения

Проект доработки. Статус: **этапы 0, 1, 3 и 4 реализованы** (2026-09-23,
образ `1c-facade:local` 0.2.0, гейты зелёные, смоук на живом парке); этап 2
(расширения) — нет.

Отклонения этапов 3–4 от текста ниже:

- имена проброса — `code_verify_xml`, а не `code.verify_xml`: API Claude не
  принимает точку в имени инструмента;
- `docs` не добирает из `codecheck` «при пустой выдаче»: поиск по документации
  ранжирует без порога и пустым не бывает. Маршрут — точное имя в `docinfo`
  (он умеет «не найдено»), иначе `docsearch`, ИТС отдельно;
- у `lint` три режима: `syntax`, `check` (корректность), `review` (стиль);
- `list_changed` не шлётся: транспорт — простой HTTP без потока. Инструмент
  лежавшего бэкенда появляется на следующем `tools/list`;
- `remember` / `recall` сервера шаблонов не публикуются — это дубль memora.

Поверхность после этапов 3–4: 9 глаголов + 8 проброшенных инструментов,
12,5 тыс. символов схем против 30,8 тыс. у прямого подключения.

Что выяснилось при реализации и в план не входило:

- `get_module_structure` принимает только абсолютный путь внутри контейнера
  бэкенда → поле `code_root` у бэкенда в реестре.
- `inspect_form_layout` у всех проверенных баз отдаёт только дерево элементов;
  реквизиты, команды и обработчики формы пусты. Парсер их понимает, живым
  ответом не проверен.
- Отказ бэкенда (`status: error`) теперь `not_found`, а не «дрейф формата».
- Гонки после снятия глобального лока нашлись в двух местах: ленивая сборка
  резолвера (ERP — минута, два одновременных вызова строили бы дважды) и
  холодный старт контейнера в `Health.ensure`. Оба под своими локами, первая
  покрыта тестом на четыре параллельных вызова.
- У `bl` коллекция `metadata` code-бэкенда пуста — `metadatasearch` всегда
  отвечает grep-слоем. Состояние бэкенда, не фасада; фасад это помечает.

Опорные документы: [`README.md`](README.md) — почему фасад устроен так;
[`RUNBOOK.md`](RUNBOOK.md) — карта парка и операции.

## Цель

`.mcp.json` проекта сводится к двум записям: `1c-facade` и `memora`. Всё, что
касается конкретной конфигурации 1С (индексы кода и графа) и всё, что
относится к платформе (справка, ИТС, проверка кода, шаблоны), приходит через
фасад. Память остаётся снаружи: это общий сервер операционной памяти, не
привязанный к 1С, с собственной моделью данных и мутирующими операциями.

Целевые клиенты — Claude Desktop и Claude CLI. Схемы там подгружаются лениво,
в контекст сразу едут только имена инструментов, поэтому **экономия поверхности
перестала быть главным призом**. Остаются три причины, ради которых фасад живёт:
маршрутизация вместо выбора по похожим описаниям, слияние выдач разных
бэкендов и блок `coverage`, отличающий «объекта нет» от «бэкенд выключен».
Отсюда правило проектирования: **глагол там, где есть выбор между
дублирующими бэкендами; сквозной проброс там, где инструмент единственный.**

Замер поверхности на 2026-09-20 (без memora): 35 инструментов, 30 800 символов
схем у четырёх серверов платформы плюс code-бэкенд проекта; у фасада — 6
инструментов, 3 070 символов.

## 1. Адресация: несущая база и именованные расширения

Сегодня `Project` плоский: имя, выгрузка, `{code, graph}`, алиасы, `frozen`.
Парк Project_BL так не описывается — там несущая база ERP и несколько
именованных расширений, имя расширения совпадает с префиксом контейнеров
(`ulk_*`, `bl_*`, `bki_*`, `lk_*`). Сейчас они лежат в реестре как пять
независимых проектов, и связь «расширение — база» существует только в
комментарии.

### Реестр v2

```json
{
  "version": 2,
  "default": "bki",
  "projects": {
    "erp": {
      "source": "/srv/sources/erp",
      "aliases": ["база", "управлениепредприятием"],
      "backends": {},
      "extensions": {
        "bki": { "source": "/srv/sources/bki", "backends": { "code": {...}, "graph": {...} }, "frozen": false },
        "lk":  { "source": "/srv/sources/lk",  "backends": { "code": {...}, "graph": {...} }, "frozen": false },
        "ulk": { "source": "/srv/sources/ulk", "backends": { "code": {...}, "graph": {...} }, "frozen": true },
        "bl":  { "source": "/srv/sources/bl",  "backends": { "code": {...}, "graph": {...} }, "frozen": true }
      }
    },
    "ec": {
      "source": "/srv/sources/ec",
      "aliases": ["эквадор", "contabilidad"],
      "backends": { "code": {...} }
    }
  }
}
```

Конфигурация без расширений (`ec`) описывается как раньше — `extensions`
необязателен. Загрузчик принимает и v1 (файл без `version`), чтобы обновление
образа не требовало одновременной правки реестра на всех машинах.

### Обращение

Все глаголы получают необязательный `scope`:

| `scope` | что опрашивается |
| --- | --- |
| `all` (по умолчанию для `find`, `usages`) | база и все расширения, выдачи сливаются |
| `base` | только несущая база |
| `<имя расширения>` | база + это расширение (расширение без базы бессмысленно) |

Совместимость: `project="bki"` продолжает работать — имя расширения
разрешается в пару `(erp, bki)`. Это же снимает вопрос миграции: старые вызовы
попадают в `scope=<ext>`.

### Слияние базы и расширения

Записи несут `scope` (`base` | `ext:<имя>`) — без этого выдача по двум
источникам неотличима от выдачи по одному. Правило порядка: расширение выше
базы при совпадении квалификатора, обе записи остаются. Если резолвер видит у
метода расширения директиву `&Вместо` / `&Перед` / `&После`, запись базы
помечается `overridden_by: ext:<имя>`; это единственное место, где фасад
что-то знает про семантику расширений, и оно стоит того — иначе `find` по базе
показывает код, который в рантайме не исполняется.

## 2. Покрытие проектных бэкендов

Сейчас фасад зовёт у code-бэкенда шесть инструментов из пятнадцати:
`search_function`, `metadatasearch`, `codesearch`, `get_metadata_details`,
`graph_dependencies` и `stats` (для health). Дыры и что с ними делать:

| Глагол | Сейчас | Становится |
| --- | --- | --- |
| `find(kind=routine\|any)` | резолвер + `code.search_function` | без изменений, плюс `scope` |
| `find(kind=metadata)` | `code.metadatasearch`, **сырой JSON** | нормализованные записи (новый парсер) |
| `find(kind=text)` | `graph.search_code` + `code.codesearch`, **сырой JSON** | нормализация `codesearch`; веер параллельный (см. этап 0) |
| `find(kind=form)` | **объявлен в схеме, не реализован** — падает в ветку `text` | `code.search_forms` |
| `describe` (объект) | `graph.get_object_dossier` + `code.get_metadata_details` | без изменений |
| `describe` (форма) | — | `code.inspect_form_layout`, когда `id` — форма или `sections=["form"]` |
| `describe` (модуль) | — | `code.get_module_structure`, когда `id` — модуль |
| `calls` | только `graph.trace_call_chain` | фолбэк на `code.get_method_call_hierarchy`, когда graph не объявлен или недоступен (**парсер `parse_call_hierarchy` уже написан и покрыт тестами, просто не подключён**) |
| `usages` | graph + `code.graph_dependencies` + резолвер | без изменений, плюс `scope` |
| `status(reindex=true)` | пересобирает только индекс резолвера | плюс `code.reindex` на бэкенде проекта |

Остаётся сквозным пробросом (этап 4): `verify_xml`, `get_xsd_schema`,
`bsl_scope_members`, `helpsearch`. Выбирать там не из чего, сворачивать в
глагол нечего.

## 3. Серверы платформы

В реестр — секция `shared` (бэкенды без проекта, health через `ping`):

```json
"shared": {
  "docs":      { "url": "http://<хост>:8003/mcp" },
  "codecheck": { "url": "http://<хост>:8007/mcp" },
  "syntax":    { "url": "http://<хост>:8002/mcp" },
  "templates": { "url": "http://<хост>:8004/mcp" }
}
```

Три новых глагола — ровно там, где сегодня модель выбирает между похожими
описаниями:

- `docs(query, scope=platform|its|any)` — `docs.docsearch` / `docs.docinfo` +
  `codecheck.search_1c_documentation` / `onec_help` / `its_help` / `fetch_its`.
  По замерам веера решить, союз или приоритет; до замеров — приоритет
  `docs`, добор из `codecheck` при пустой выдаче.
- `lint(code|path, mode=syntax|review)` — `syntax.syntaxcheck` +
  `codecheck.check_1c_code` / `review_1c_code`. `syntax` — быстрый гейт,
  `review` — тяжёлый; смешивать их в один вызов нельзя, поэтому режим явный.
- `template(query)` — `templates.templatesearch` / `get_template`.

`ask_1c_ai` (Напарник) под глагол не идёт: это генеративный ответ, а не поиск,
и его место — сквозной проброс рядом с `verify_xml`.

## 4. Этапы

**Этап 0 — фундамент** (полдня). Снять глобальный `threading.Lock` в
`Dispatcher._call` (сейчас он сериализует все вызовы фасада); сделать веер в
`find(kind=text)` действительно параллельным — в коде два последовательных
`_ask`, хотя README обещает `max(t1, t2)`; вынести таймауты бэкендов в реестр.

**Этап 1 — ядро** (день). `calls` с фолбэком на code; `find(kind=form)`;
`describe` для форм и модулей; парсеры `metadatasearch` и `codesearch`;
`status(reindex=true)` доходит до бэкенда. Покрытие code-бэкенда: 6/15 → 12/15.
После этого прямой `1c-code-metadata-mcp` можно убирать из `.mcp.json` без
потери функциональности.

**Этап 2 — расширения** (2–3 дня). Реестр v2, `scope`, слияние с пометкой
`overridden_by`, резолвер по нескольким выгрузкам, миграция Project_BL.

**Этап 3 — платформа** (2–3 дня). Секция `shared`, глаголы `docs`, `lint`,
`template`, health через `ping`.

**Этап 4 — проброс хвоста** (день). Поле `expose` в записи бэкенда: список
инструментов, публикуемых поимённо с префиксом (`code.verify_xml`,
`code.get_xsd_schema`, `code.bsl_scope_members`, `code.helpsearch`,
`shared.ask_1c_ai`). Схема приезжает от бэкенда при старте, вызов проксируется
один в один, ответ не нормализуется. Маршрут задан данными, а не кодом.

Итог: `tools/list` — 9 глаголов + 5–6 проброшенных инструментов, порядка
8 КБ схем. `.mcp.json` проекта — `1c-facade` и `memora`.

## 5. Тесты и риски

Конвейер фикстур не меняется: `capture.py` → `anonymise.py` →
`test_parsers.py --update`. Новые кейсы: `code_search_forms__ok`,
`code_form_layout__ok`, `code_module_structure__ok`, `code_metadatasearch__ok`,
`code_codesearch__ok` плюс пустые ответы для каждого. В `test_facade.py` —
фейковые клиенты для `shared` и сценарий «graph нет → calls отвечает из code».

Риски:

1. **Время старта.** Резолвер уже сейчас греет индексы всех проектов при
   запуске; с расширениями источников станет больше. Смягчение: `frozen` для
   снимков уже есть, прогрев фоновый, `status` отвечает без индекса.
2. **Перекрытие base/ext** — самая содержательная новая логика и главный
   источник ложных ответов, если ошибиться. Держать отдельный набор тестов на
   паре «метод базы + `&Вместо` в расширении».
3. **Проброшенные схемы стареют.** `expose` тянет схемы у бэкенда при старте;
   если бэкенд лежал, инструмента в `tools/list` не будет. Лечится
   перечитыванием при первом успешном health и уведомлением
   `notifications/tools/list_changed`.
4. **Глаголы `docs`/`lint` могут оказаться беднее прямых вызовов** — у
   `fetch_its` и `review_1c_code` есть параметры, которые в глагол не влезут.
   Если после этапа 3 всплывут потери, эти инструменты уходят в `expose`, а не
   наоборот.

## 6. Что не делаем

- **memora** через фасад не проксируется.
- **Профили наборов инструментов** (разный `tools/list` по проектам) — отложены
  до появления реальной разницы между проектами.
- **Cursor и прочие клиенты без ленивой загрузки схем** не являются целью;
  решения принимаются исходя из Claude Desktop и CLI.
