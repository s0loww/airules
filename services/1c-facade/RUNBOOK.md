# Фасад: эксплуатация

Что делать в конкретной ситуации. Почему устроено именно так — в
[`README.md`](README.md).

## Карта парка

Имена контейнеров — по `Configuration.xml` выгрузки, а не по каталогу или
исторической привычке. Проверять расхождение так:
`grep -m1 '<Name>' <выгрузка>/Configuration.xml`.

| проект | конфигурация | выгрузка | контейнеры | порты |
| --- | --- | --- | --- | --- |
| `bl` | БалтийскийЛизинг 2.5.22 | `1c-config-dumps/ERP_BL` | `bl_code_metadata`, `bl_graph_metadata`, `bl_neo4j` | 8012, 8013 |
| `ulk` | УправлениеЛизингом 2.5.22 | `Project_BL/src` | `ulk_*` | 8016, 8006 |
| `bki` | КонтурБКИ 1.0.0 | `Project_BL/src_bki` | `bki_*` | 8014, 8015 |
| `erp` | УправлениеПредприятием 2.5.22.166 | `Project_BL/erp_crc` | **нет** | — |
| `ec` | Contabilidad 2.7.13 (Эквадор) | `Эквадор/src/main` | `ec_code_metadata` (graph нет) | 8000 |

Фасад — `1c_facade`, `127.0.0.1:8770`. Бэкенды он зовёт по **имени контейнера**
во внутренних сетях (`code` на 8000, `graph` на 8006); порты в таблице нужны
только для ручной диагностики.

`erp` — база, которую расширяют все три расширения. Бэкендов у неё нет, и это
рабочее состояние: `find(kind=routine)`, `usages(where=code)` и канонизация имён
идут из собственного индекса фасада, а `calls` и `describe` честно сообщают, что
бэкенда нет.

## Обычные операции

**Поднять / пересобрать фасад**

```bash
docker compose -f services/1c-facade/docker-compose.yml up -d --build
```

Старт парка — около 8 с: пересканируется только активный проект, остальные
открываются как снимки.

**Посмотреть, что живо**

```
status()                      # весь парк
status(project="bl")          # один проект
```

**Сменить активное расширение.** В `facade-registry.json` снять `frozen` с
нового активного и поставить остальным, затем перезапустить контейнер. Активным
должно быть ровно одно — то, в котором сейчас идёт работа.

**Обновили выгрузку-снимок на диске**

```
status(project="ulk", reindex=true)
```

Реестр править и перезапускать ничего не нужно.

**Добавить проект.** Запись в `facade-registry.json` (имя — из
`Configuration.xml`), монтирование выгрузки `:ro` в `docker-compose.yml`,
перезапуск. Если у проекта есть свои бэкенды — фасад должен быть подключён к их
сети (`networks:` в compose).

**Подключить целевой проект.** Одна строка в его `.mcp.json`, одинаковая для
всех:

```json
{ "mcpServers": { "1c-facade": { "type": "http", "url": "http://127.0.0.1:8770/mcp" } } }
```

Записи code/graph-серверов из `.mcp.json` при этом убираются — их заменяет
фасад. Справочные и корпусные серверы (ИТС, БСП, шаблоны, синтакс-чекер,
память) остаются: фасад их не покрывает.

## Что означает состояние бэкенда

| состояние | что произошло | что делать |
| --- | --- | --- |
| `up` | отвечает | — |
| `up` + `indexing` | отвечает, но индекс ещё строится | подождать; **пустая выдача сейчас значит «ещё нет», а не «нет такого»** |
| `cold` | контейнер есть, остановлен | поднять; либо `cold_ok` в реестре, если можно будить автоматически |
| `down` | контейнера нет либо старт отклонён | проверить compose стека бэкенда |
| `unknown` | не достучались и не смогли спросить демона | обычно сеть: контейнер не в той сети, что фасад |

Любой ответ, которому не хватило бэкенда, помечается `degraded` и словами
называет, чего именно не хватило. Пустой ответ без `degraded` означает
буквально «не найдено».

## Типовые поломки

**Порт занят посторонним контейнером.** Симптом самый неприятный: сервер
отвечает, но **не про ту конфигурацию**. Так `.mcp.json` месяцами ходил на 8005
и получал ответы из индекса CUL, потому что тот занял порт, объявленный в
compose для другого стека, и настоящий контейнер поднялся без маппинга.

Диагностика — сверить масштаб с выгрузкой:

```bash
# modules в ответе должно совпадать с числом .bsl в выгрузке
find <выгрузка> -name '*.bsl' | wc -l
```

Лечение: переселить на свободный порт в compose своего стека и пересоздать.
Для фасада порт вообще не важен — он ходит по имени контейнера, — но контейнер
обязан быть **в сети** своего стека.

**`unknown` у всех бэкендов одного стека.** Фасад не подключён к сети этого
стека. Добавить её в `networks:` его compose (сети объявлены `external: true`).

**Индекс базы строится десять минут.** Так и есть: перехеширование 121 648
файлов через bind-mount. Для того и `frozen` — снимок индексируется однократно.
Если индекс пропал, он лежит в томе `facade-state` как `index-<проект>.sqlite`.

**Фасад не видит изменений реестра.** Реестр читается при старте, файл
смонтирован `:ro`. Перезапустить контейнер.

## Чего не трогать

- **Имена томов** — держат данные. Переименование = потеря индексов.
- **`PROJECT_NAME`** у graph-серверов — партиционирует граф в neo4j.
  Смена = переиндексация, а она платная (эмбеддинги идут в OpenRouter).
- **Сокет docker** в compose закомментирован. Он нужен только чтобы фасад сам
  будил остановленные бэкенды (`cold_ok`), и это доступ к демону хоста,
  равносильный root. Без него всё работает, кроме автоподъёма.

Расхождение между именем контейнера и `PROJECT_NAME` оставлено намеренно и
задокументировано комментарием в compose обоих стеков — чтобы через полгода оно
не выглядело недосмотром.

## Проверки

```bash
python test_parsers.py      # парсеры прозы бэкендов: инварианты + снапшот
python test_facade.py       # резолвер, реестр, глаголы (на реплее фикстур)
python test_server.py       # протокол сквозь настоящий сокет
```

Живых серверов не требуют. Обновился образ бэкенда и парсер поехал — гейт
покажет, где именно: каждый парсер сверяет число, объявленное сервером в шапке,
с числом разобранных записей. Перезаснять фикстуры:
`python capture.py && python anonymise.py && python test_parsers.py --update`.
