# Как контрибьютить в airules

## Входной фильтр обязателен

Любая практика перед попаданием в дистрибутив проходит входной фильтр из
[`LAYERS.md`](LAYERS.md). Без ответа на три вопроса фильтра артефакт не
принимается. При сомнении — слой ниже (ближе к проекту).

Перед предложением сверься с базой отклонённого:
[`out-of-scope/`](out-of-scope/README.md) — совпадение по смыслу концепта
либо подтверждает отклонение, либо осознанно переоткрывает его.

## Куда что кладётся

| Слой | Каталог | Что здесь |
| --- | --- | --- |
| core | `core/` | Generic-метод: роли, роутинг моделей, контракты, делегирование. Ноль домена. |
| overlay | `overlays/<stack>/` | Специфика стека, не проекта. |
| project | `project-template/` | Только шаблон проектного слоя; контент проектов не коммитится. |

## Проверка перед коммитом

Перед коммитом прогони проверку чистоты слоёв:

```sh
python ci/check_layers.py
```

pre-commit хук делает это автоматически для staged-файлов. После клона
репозитория включи хуки:

```sh
git config core.hooksPath .githooks
```

Прогнать самотест правил по фикстурам:

```sh
python ci/check_layers.py --selftest
```

Если строка-пример в документации законно содержит запрещённый паттерн (имя
модели, доменное имя и т.п.), пометь её маркером `airules:allow <rule-id>` — эта
строка будет исключена только из указанного правила.

## Как писать правило

Правило существует, чтобы выжать предсказуемость из стохастической системы:
агент проходит один и тот же *процесс* на каждом запуске. Рабочие приёмы
(адаптировано из `writing-great-skills`, mattpocock/skills, MIT):

- **Тест на no-op.** Строка, которую модель и так исполняет по умолчанию, —
  шум: она не меняет поведение, но ест токены на каждой загрузке. Тест —
  «изменит ли эта строка поведение относительно дефолта модели?»; спор
  решается прогоном, а не дебатами. CI-правило `stale-verification`
  (запрет формулировок самоперепроверки) — частный случай этого теста,
  зашитый в проверку.
- **Прунинг предложениями.** Провалившее тест предложение удаляется
  целиком, а не подрезается по словам. Большинство слабой прозы надо
  удалять, а не переписывать.
- **Опорные слова.** Рулить компактным термином, который уже живёт в
  претрейне модели (seam, dry run, write zone, red, frontier), и повторять
  его как токен, а не пересказывать определение. Выдуманный термин не
  подтягивает приоры — за него платишь токенами определения.
- **Позитивные формулировки.** Запрет называет запрещаемое и делает его
  доступнее («не думай о слоне»). Описывай целевое поведение; голый запрет
  оставляй только как жёсткий guardrail и спаривай с позитивной целью.
- **Раскрытие по ветвлению.** Инлайнить то, что нужно на каждом проходе
  правила; выносить в отдельный файл/секцию то, до чего доходят только
  некоторые ветки. Must-have материал за слабо сформулированной ссылкой —
  баг формулировки ссылки, а не повод инлайнить всё.
- **Description = указатель контекста.** Формулировка `description` во
  frontmatter решает, дотянется ли агент до правила в нужный момент: один
  триггер на ветку применения, без синонимов-дублей, русские триггеры
  хвостом (языковая политика ниже).

## Языковая политика дистрибутива

- **Тела** правил, ролей, скиллов, команд и шаблонов — на **английском**:
  это дешевле по токенам (кириллица токенизируется в ~1.5–2 раза дороже)
  и точнее попадает в устоявшуюся агентную терминологию (write zone, stop
  rules, dry run).
- **Доменная терминология 1С** в оверлее — **по-русски, без перевода**
  (реквизит, проведение, СКД…): знания моделей об 1С и код целевых проектов
  русскоязычны, перевод снижает точность.
- **`description` во frontmatter** — двуязычный: английская база + хвост
  `Триггеры: <русские ключевые слова>` для роутинга по русским запросам.
- **Язык ответов** пользователю задаётся `LANGUAGE_POLICY` в корневом
  контракте и не зависит от языка инструкций.
- Миграция — по мере правок файла, не большим взрывом; оставшиеся
  русскоязычные файлы перечислены в [`TODO.md`](TODO.md).

## Сборка дистрибутива (инсталлятора)

Сборка делается из git-тега — только закоммиченный контент, eol по
`.gitattributes`:

```sh
git archive vX.Y.Z | tar -x -C <папка-сборки>
rm -rf <папка-сборки>/CLAUDE.md <папка-сборки>/.rtk <папка-сборки>/.claude   # dev-файлы этого репо
```

Папку прошлой сборки не перезаписывать поверх — удалённые из дистрибутива файлы
остались бы в ней. Прежнюю сборку переименовать (`<папка>-<версия>`) и
распаковывать в пустую.

Проверка сборки: `VERSION` совпадает с тегом; `python ci/check_layers.py`
из корня сборки — ноль нарушений; `ONBOARD.md` и `SOFTWARE.md` на месте.
Получателю сборки достаточно открыть папку своим агентом и дать ему
`ONBOARD.md` (см. `README.md`, «Установка»).

## Правило коммитов и версий

Механизм и контент — **отдельными коммитами**. Изменение скрипта проверки,
хука или структуры слоёв не смешивается с добавлением правил/ролей/практик.

Дисциплина версии: `VERSION` бампится **в том же коммите**, который считается
релизным, и тег `vX.Y.Z` ставится на этот же коммит; коммит с сообщением
«vX.Y.Z: …» без бампа `VERSION` и тега на нём — ошибка. Контент, добавленный
после тега, до следующего бампа считается нерелизнутым и в манифесты
установок не попадает.
