# Универсальный механизм проверок и deploy: первая интеграция с 1С/DSH

Дата: 2026-11-04. Статус: **Proposed**. Это проект решения по результатам
чтения исходников, не разрешение на выполнение и не протокол тестирования баз.

Исполняемый инкремент 1: [core и CLI](../core/tools/workflow/README.md) и
[offline domain gate](../overlays/1c/tools/workflow-onec/README.md) реализованы.
Общая архитектура остаётся Proposed. Следующий инкремент установлен в DSH:
штатные права/песочница, интерфейс workflow и адаптеры проектных runners.
Исполнитель `deploy-apply` реализован и проверен на заглушках: связанный отчёт,
вычисленная цель, блокировки и штатный native subprocess. Текущий установленный
исходный режим fixture-only запрещает реальное применение. В policy dev25
поддержаны файловая и серверная 1С test/development, deploy-preview, сохранение
сценария и режима из интерфейса, доказательное восстановление через fixture,
проверенный локальный runner или отдельно настроенный MCP provider. Реальные
базы и recovery providers не запускались. Подробности:
[workflow release](D:/AI_Projects/dsh_harness_overlay/docs/workflow-complete-release.md).

## Контекст

Обсуждается перенос проверок и deploy из сборки Олега в нашу установленную DSH.
Политику распространяем из project_rules, подключение MCP оставляем внешним.
Эквадор, КА2 и БЛ уже имеют собственные инструменты и разные тестовые контуры.
Уточнение пользователя: MCP-фасад относится к соответствующим MCP-инструментам,
а не к деплою/тестовым runners. Их исполнитель вызывает напрямую через adapters.
Отдельные проектные ONEMCP/QA подключаются явно. Сценарий на project_bki пропущен.
Фасад может отсутствовать полностью: у другого получателя сборки допустимы
несколько прямых MCP одного проекта. Это штатная конфигурация, не degraded
установка. Наш личный способ подключения не является требованием preset.

Отдельный DSH `airules_verification` только сообщает правила и bindings:
`status=declarative-only`, `executesChecks=false`
([verification.mjs](D:/AI_Projects/dsh_harness_overlay/src/airules-provider/verification.mjs:1)).
Наличие пресета, профиля или функции runner не доказывает настроенный канал.

Три проверенных проекта требуют разных адаптеров:

| Проект | Реальная основа | Что нельзя принять за готовый общий pipeline |
|---|---|---|
| Эквадор | `scripts/TestEnv.ps1`, импорт main + TestingExtension, собственный unit engine/JUnit | Generic agent-1c старее, корневого профиля нет. RunUITests — ручной launcher без автоматических UI-сценариев. Выбор платформы нужно закрепить точным build. |
| КА2 | Два профиля agent-1c для отдельных расширений; общий guarded runner | Unit и postdeploy probe в профилях не заданы. Старый update-ka2-extension выполняет изменения по умолчанию. |
| БЛ | Четыре профиля agent-1c; отдельные LK acceptance и БКИ bench | Unit/probe не настроены. Server-профиль несовместим с file-only Vanessa. Старый Deploy-LK имеет другие lock/verdict и вывод argv с паролем. |

Подробные основания и точные строки кода: аудит
[Эквадора/КА2](D:/AI_Projects/dsh_harness_overlay/docs/audits/ecuador-ka2-checks-deploy.md)
и [БЛ](D:/AI_Projects/dsh_harness_overlay/docs/audits/bl-checks-deploy.md).
Личные пути здесь служат ссылками на аудит, не параметрами распространяемого пресета.

В сборке Олега `onec_deploy check` выполняет LoadConfigFromFiles и тем самым
меняет конфигурацию базы, хотя UpdateDBCfg выключен. Автоматического DB rollback
в этом центре нет. Его полезные части — явный scope/plan, drift/path guards,
учёт stale/partial evidence, последовательный batch, ownership и cancel.
Низкоуровневые default-on UpdateDB/dynamic, очистка .cfl, автоматический Git
commit и прямые raw MCP привязки в наш общий preset не переносятся.
Точный разбор: [аудит Олега](D:/AI_Projects/dsh_harness_overlay/docs/audits/oleg-checks-deploy.md).

## Решение

**Общее ядро workflow и исполнения, доменные пакеты и подключаемые адаптеры.**

Уточнение пользователя от 2026-11-04: механизм должен быть максимально
универсальным. Три исследованных проекта — приёмочные примеры, не перечень
встроенных веток. Ядро не знает имён проектов, команд Designer, XML-структуры
1С, формата JUnit или названий DSH tools. Существующие ограничения 1С сохраняет
доменный пакет. Универсальность не означает автоматическое разрешение новых
операций, произвольный shell или обещание поддержки всех платформ сразу.

### Границы расширения

| Компонент | Ответственность | Как расширять |
|---|---|---|
| Workflow core | Граф шагов, plan/run, состояния, обязательные gates, блокировки ресурсов, журнал | Без условий по имени проекта, ОС или технологии |
| Domain pack | Семантика source/target, workflows, ограничения и validators домена | Первый — 1С; Python/sysadmin могут подключаться позже без изменения core |
| Execution adapter | Версионированный контракт конкретного runner/движка, обнаружение возможностей, преобразование результата | agent-1c, TestEnv, проверенная предметная suite; adapter переиспользуется между проектами |
| Evidence validator | Разбор формата и проверка полноты/свежести/утверждений | JUnit, Designer result, предметный JSON/протокол; exit=0 сам по себе не общий validator |
| Worker/transport | Исполнение на подходящем host, identity, ownership, доступ к секретам | Windows — первый host для 1С, не обязательная ОС ядра |
| Client | Настройки, просмотр плана и отчёта | DSH — первый UI; core API допускает CLI/CI с теми же gates |
| Project binding | Данные: источники, targets, suites, разрешённые capabilities и выбранные профили | Новый типовой проект подключается данными, без копирования core или персонального adapter |

Один workflow может соединять разные adapters и targets: например, статический
анализ → резервирование → загрузка → проверка модулей → предметный тест.
Adapter требуется только для нового способа исполнения/протокола; отдельный
adapter на каждую базу или проект не создаётся. Проектный wrapper допустим для
действительно уникального runner и должен явно объявлять ограничения.

Workflow содержит versioned step definitions, зависимости, typed inputs/outputs,
требуемые capabilities и эффекты. Общие workflows поставляются как шаблоны;
проект выбирает и уточняет их данными. Не каждый проект обязан иметь deploy
или все виды тестов. Недоступную способность нельзя подменять похожим действием.
Условия выбора/пропуска шагов сохраняются в plan и отчёте, а не решаются скрыто
моделью в середине применения.

Клиентская форма строится по разрешённой схеме параметров adapter; команда
и credentials в ней не появляются. Неподдержанная версия протокола блокирует
запуск с объяснением. Новый adapter/validator устанавливается как доверенный
компонент, а не исполняется автоматически из произвольного checkout.

```text
DSH / CLI / CI: настройки / план / запуск / отчёт
                    |
       workflow core + domain pack 1С
                    |
       локальный execution host
                    |
     утверждённый project adapter
       /              |          \
 TestEnv          agent-1c     предметная suite
```

Execution host — компонент исполнения внутри локальной интеграции DSH/CLI,
вызывающий проверенные runners напрямую. Отдельная служба, сетевой worker
или MCP-сервер для локального запуска не требуются. Удалённый host можно
добавить отдельным transport adapter, когда появится такая задача.

MCP — самостоятельный необязательный канал конкретных шагов, например анализа
через 1c-facade или предметной проверки через настроенный ONEMCP/QA. Доступность
фасада не является условием локального deploy/unit/Vanessa, если workflow явно
не требует от него результата. Существующий facade.check остаётся rules-check
([verbs.py](D:/AI_Projects/project_rules/services/1c-facade/norm/verbs.py:748));
переименовывать его в deploy или дорабатывать фасад ради исполнения не нужно.
Существующий services/agent-service не относится к этому execution host.

### Независимость от топологии MCP

Поддерживаем одинаково: без MCP, один прямой сервер, несколько прямых серверов,
фасад, смесь фасада и отдельных серверов. Ни фасад, ни memoria, ни ONEMCP/QA
не обязательны для установки. Полезность конкретного workflow определяется
его реальными зависимостями; например, локальный lint/runner может работать
при отсутствии любых MCP. Ненастроенная обязательная проверка блокирует только
зависящий от неё workflow, а не весь проект или готовность приложения.

Шаг требует семантическую capability, а binding выбирает provider: локальный
adapter либо конкретный MCP connection/tool с проверенным преобразованием
inputs/results. Имена `1c-facade`, серверов и tools не зашиваются в общий
workflow. Нельзя считать одноимённые `check` эквивалентными или подключать
первый похожий инструмент. Для разных API нужен adapter, для выбора уже
поддержанного provider — только настройка. Замена provider требует проверки
контракта и нового плана; она не выполняется скрыто при ошибке.

Project binding выбирает логические providers; пользовательские/машинные
настройки разрешают их в доступные MCP connections. Проверяются проектная
принадлежность, возможности, эффекты и разрешения. Одинаковое имя сервера
у двух пользователей не доказывает одинаковую базу. В распространяемой сборке
нет личного набора подключений: получатель использует свои существующие
MCP или настраивает новые штатным способом. Установка правил не меняет их.

Ресурс блокировки — произвольная разрешённая identity, не только база 1С:
каталог артефактов, deployment target, сервис, база. Набор и порядок захвата
объявляются планом; взаимное исключение действует между adapters и clients.
Параллельность допускается лишь для независимых ресурсов и объявленных
безопасных шагов. Мутации не повторяются автоматически без доказанной
идемпотентности конкретной операции; workflow не считается транзакцией.

### Владение настройками

| Слой | Содержимое |
|---|---|
| Встроенный preset / project_rules | Правила, capabilities, контракт, критерии результата, переносимые adapters |
| Проект | Выбранные источники/расширения, operations и ссылки на существующие профили, suite и обязательные gates |
| Машина | Регистрация разрешённых checkout, worker/transport, credential store, toolchain, фактические targets и services |
| DSH UI | Черновик и явное сохранение ссылок; план, статус и evidence. Без второй копии профиля/паролей |

`.dev.env`, каталог проекта и название базы не определяют deploy target.
Для agent-1c используется существующий профиль; для TestEnv — отдельный адаптер.
При конфликте источников конфигурации запуск блокируется, fallback на другую базу
или старый скрипт запрещён. Глобальный preset не содержит адресов баз/серверов,
секретов, персональных путей, raw MCP endpoints или произвольных shell-команд.

### Порядок и классы проверок

1. **Plan/doctor-files:** проверить binding, XML source kind, версию adapter,
   локальные инструменты и доступные capabilities. Без запуска 1С/COM, создания
   базы, остановки служб и подключения к цели. Даже проверка доступности базы
   выделяется в отдельную операцию с известными эффектами.
2. **Analyze:** XML/BSL/rules и baseline до записи. Facade lint/check и LLM review
   различаются: ответ модели не заменяет машинный verifier.
3. **Preflight:** разрешить точную identity цели и build платформы; проверить
   полномочия, взаимную блокировку, backup/rollback и необходимые зависимости.
4. **Deploy:** загрузить нужную конфигурацию/расширение проектным adapter.
   Для extension имя обязательно и сверяется с XML. File/cluster — разные engines;
   кластерная база обслуживается через кластер, не прямой ibcmd-доступ к SQL.
   Внутри плана разделить load-config → доступные проверки загруженной
   конфигурации/применимости → update-db. Где проверка применима до UpdateDBCfg,
   её отказ блокирует update; загрузка при этом уже изменила конфигурацию базы.
   Существующий runner, связывающий load+update без промежуточного gate,
   не считается автоматически поддерживающим такой безопасный разрыв стадий.
5. **Postdeploy:** проверить платформенный результат, фактическую метадату и
   проверки, требующие обновлённой БД. CheckModules-контексты и фаза каждого
   gate задаются adapter, а не одним универсальным «после deploy». Это не
   противоречит source analyze до записи.
6. **Test:** минимальный наблюдающий слой + обязательная регрессия: unit,
   данные/интеграция, роли, предметная приёмка, UI по проектной матрице.

Это граф зависимостей, а не требование каждый раз запускать все виды тестов.
Условия обязательности задаются проектом и областью изменения. Отсутствующий
обязательный канал блокирует общий PASS; отсутствующий необязательный виден явно.
Unit/UI/acceptance могут менять данные и запускать процессы даже без deploy Apply.
Warnings-as-errors из поставщика не включается скрыто: политика предупреждений
и сравнения с baseline определяется проектом, отсутствие diagnostics не угадывается.

### Запуск и гарантии

- Только зарегистрированные operation IDs и проверенные adapters. Worker не
  принимает командную строку, скрипт или путь исполняемого файла от модели.
- Plan привязан к хешам фактических исходников (включая dirty/untracked scope),
  профиля, adapter, toolchain, точной цели и набору эффектов. Изменение любого
  существенного входа делает план устаревшим; перед мутацией повторный preflight.
- Класс среды проверяется по allowlist. Неизвестный класс запрещён; отсутствие
  слова production не доказывает test. Разрешение тестового запуска не разрешает
  production. Уже выданные полномочия в рамках конкретной задачи сохраняются;
  лишние подтверждения каждой обратимой операции не вводятся.
- Все пути к одному target используют общую блокировку по разрешённой identity,
  включая backup, deploy и тесты с записью. Разные aliases не обходят lock.
- Backup: согласованный снимок или явно disposable-копия с воспроизводимым
  восстановлением. Копия открытой файловой базы не считается согласованной.
  Откат версии расширения не равен восстановлению данных/схемы.
- Остановка/возврат только объявленных services и процессов данного запуска.
  Без общего kill 1cv8/ibcmd. Отмена UpdateDBCfg может оставить неопределённое
  состояние: сначала диагностика, без автоматического повторного Apply/RestoreIB.
- Пароли разрешаются на машине, не идут в plan/result/stdout. Если runner требует
  секретный argv, отдельно фиксируется риск доступа к process command line;
  одной редактуры отчёта недостаточно. Сырые логи не публикуются без обработки.
- Run ID уникален независимо от секунды запуска; evidence не перезаписывается.
  Новая baseline создаётся отдельной операцией review, а не превращает ошибки
  первого прогона в PASS. Проверяются свежесть, provenance и полнота результатов.

Hidden desktop — опциональная реализация UI runner. Пакет hodden_test уже дал
правила для disposable copy, process ownership, JUnit/buildstatus/exit, cleanup.
Его исторический smoke не доказывает работоспособность в этих трёх проектах;
скрытое окно не подтверждает визуальную корректность и бизнес-результат.
См. [границы проверки](HIDDEN-DESKTOP-TESTING.md).

## Альтернативы

| Вариант | Плюс | Причина не выбирать основой |
|---|---|---|
| Копировать весь Oleg Full pipeline | Готовая UI-модель | Зависимости от его правил/каналов и несовпадение с нашими реальными runners |
| Везде заменить на agent-1c | Один CLI | Потеря Ecuador TestEnv/engine и предметных suite; нынешние guards не закрывают все пробелы |
| Произвольная shell-команда из UI/модели | Быстрое подключение скрипта | Нет проверенного контракта параметров, эффектов и результата |
| Локальный execution host + project adapters | Сохраняет проектные практики, прямой запуск и единый отчёт | Нормализация evidence и отдельная проверка каждого adapter |

## Последствия и порядок реализации

1. **Закрыть контракт:** согласовать модель plan/result и реестр эффектов;
   подготовить secret-free fixtures трёх проектов. Проверка схем и планирования
   не требует платформы или базы. Черновик контракта —
   [DSH-CHECKS-DEPLOY-CONTRACT.md](DSH-CHECKS-DEPLOY-CONTRACT.md).
2. **Усилить canonical runner:** полная schema validation, strict target allowlist,
   точный build/source-kind, UUID evidence, единый lock, свежий DumpResult/Out,
   корректные unit/Vanessa verdict, запрет автоматического принятия baseline,
   backup receipts и честный признак applied/unverified. Затем отдельно раскатать
   в проекты, не перетирать TestEnv и предметные suite.
3. **Локальный execution host:** регистрации проектов, ограниченные операции, ownership,
   отмена, secret handling, capability discovery. Контрактные тесты на fake runner:
   stale plan, target mismatch, alias lock, неверная схема, missing/zero/stale
   JUnit, timeout, partial apply, отмена и redaction. Лишь затем подключение DSH.
4. **UI:** разделы «Проверки», «Деплой», «Прогоны» в проектных настройках;
   таблица настроенных/недоступных каналов, цель/источник/build, эффекты и backup,
   просмотр плана перед Apply, журнал и отдельный статус после загрузки.
5. **Проектная проверка:** сначала изолированный unit-контур Эквадора; затем
   явно выбранный file target КА2; потом соответствующий контур БЛ. Для каждого
   сначала plan и негативные проверки, затем отдельно разрешённый тестовый прогон.
   Эта последовательность — предложение, не запуск сейчас и не возврат к БКИ.

Для адаптера Эквадора до исполнения отдельно закрыть timeout ENTERPRISE,
ненулевое число тестов, сохранение уникальных логов и запрет широкого завершения
ibcmd-процессов из UI launcher. Ручной RunUITests не запускать фоновым gate.
Для КА2/БЛ не объявлять unit/probe настроенными до появления реальных bindings;
старые mutable-by-default wrappers остаются вне автоматического fallback.

Критерий готовности исполнения: обязательные gates подтверждены свежим evidence,
получены негативные результаты для неверной цели/плана, мутации ограничены
объявленным контуром, восстановление/cleanup проверены. Пока этого нет,
установленная capability остаётся declarative-only.
