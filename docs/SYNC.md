# Синхронизация дистрибутива

Выбранная модель распространения — **отдельный репозиторий + релизы + манифест
установки**. Решение принято; `git subtree` описан ниже как опция, а не как
дефолт.

## Версии

Дистрибутив = этот репозиторий. Версии помечаются git-тегами `vX.Y.Z` и
дублируются в файле `VERSION` (semver). Пока без remote — репозиторий локальный.

## Установка

Агент-инсталлятор копирует выбранные слои в целевой проект и записывает в его
корень `.airules-manifest.json`:

```json
{
  "version": "<из VERSION дистрибутива>",
  "installed_at": "<ISO-8601 timestamp>",
  "files": { "<relative-path>": "<sha256>" },
  "placeholders": { "<PLACEHOLDER>": "<заполненное значение>" }
}
```

Установка без записи манифеста **запрещена**: без манифеста последующее
обновление невозможно. Секреты в `placeholders` **не пишутся** (ONBOARD §8).

Алгоритм хеша — **SHA-256 от байтов файла как есть** (без нормализаций
содержимого), hex в нижнем регистре, 64 символа. Эквивалентные команды:
PowerShell `Get-FileHash -Algorithm SHA256`, Python
`hashlib.sha256(open(p,'rb').read()).hexdigest()`.

**Следствие: переводы строк обязаны быть зафиксированы.** Раз хеш берётся от
сырых байтов, любая подмена переводов строк ломает сверку. При
`core.autocrlf=true` (дефолт git для Windows) и без `.gitattributes` в цели
checkout переписывает LF на CRLF — и обновление видит изменённым **каждый**
управляемый файл. Поэтому установка кладёт в корень цели `.gitattributes` из
`project-template/gitattributes.example` (ONBOARD §4.7), пиная текст в LF, а
`*.ps1` в CRLF, и покрывает только управляемые пути. Проверка — `git
ls-files --eol`: колонка `w/` обязана совпадать с тем, что предписывает
`attr/`.

## Обновление

Для **копируемых как есть** файлов инсталлятор сверяет sha256 каждого
установленного файла с манифестом:

- **не изменён пользователем** → заменить новой версией из дистрибутива;
- **изменён пользователем** → спросить: оставить как есть или перезаписать, сняв
  бэкап в `.rules-backups/<timestamp>/`;
- **новый файл в дистрибутиве** → добавить; новое **правило** дополнительно
  вносится в Rule Index пересборкой листингом (ONBOARD §4.2) — независимо от
  того, менялся ли шаблон `AGENTS.md`;
- **удалён из дистрибутива** → предложить удалить у пользователя.

Три класса файлов sha-сверкой **не** обновляются (полная процедура — ONBOARD §9):

- **Генерируемые файлы** (`AGENTS.md`, `openspec/project.md` — параметризованы
  фактами целевого проекта): «версии из дистрибутива» у них не существует, их
  «источник изменился» определяется по диффу шаблона-источника между версиями
  дистрибутива. Шаблон изменился → обновить **слиянием**, сохранив заполненные
  факты; не изменился → не трогать.
- **Рендер-добавки адаптера** (стандартные блоки, которые инсталлятор добавляет
  в канальные представления агентов при рендере — см. `core/channels/adapters.md`):
  если между версиями изменились правила рендера, а не тела ролей —
  переприменить рендер к канальным представлениям, тела ролей не трогая.
- **Отрендеренные agent definitions** (`.claude/agents/*.md`,
  `.codex/agents/*.toml` и аналоги): «версии из дистрибутива» у них тоже нет —
  они продукт рендера тел ролей. Если между версиями изменились сами тела
  ролей или их tier/effort/tools в реестре → **перерендерить** затронутые
  определения по процедуре установки (тело + блок дисциплины + профиль
  модели); локальные правки пользователя ловятся манифестом и решаются общей
  развилкой (спросить, бэкап). Тела не менялись → не трогать.

В конце обновления манифест **переписывается**: новый `version`, свежий
`installed_at`, пересчитанные `files`, актуальные `placeholders`.

### Обновление на 0.5.0 — черновик (контент после тега v0.4.0, не зарелижен)

Кроме штатной sha-сверки следующее обновление требует:

- **Rule Index пересобрать листингом** — в core добавлены новые правила
  (debugging-loop, test-discipline, session-handoff, decision-interview);
  шаблон `AGENTS.md` тоже менялся, но пересборка индекса обязательна
  независимо от этого.
- **Перерендерить agent definitions** — менялись тела ролей core (analytic,
  code-reviewer, planner) и оверлейных агентов 1С (code-reviewer, developer,
  refactoring); класс «отрендеренные agent definitions» выше.
- **Мигрировать строку отладки роутинг-таблицы** — в 0.4.0 она была
  плейсхолдерной (у 1С-установок заполнена доменным правилом), теперь ядро
  строки — `debugging-loop`, оверлейная адаптация дописывается рядом
  (примечание таблицы в шаблоне).
- **Отрендерить пару условного тира** — `analytic` теперь ставится двумя
  определениями (`analytic` + `analytic-deep`, adapters §1 шаг 7); добавить
  вторую строку в `{{AGENTS_TABLE}}`.
- **Переклассифицировать MCP-инвентарь** — каждому серверу присвоить
  `access: ro|rw` (ONBOARD §1.1, при сомнении rw, подтвердить у пользователя)
  и перегенерировать allowlist ro-ролей на каналах с машиночитаемым
  allowlist: `rw`-серверы из ro-ролей убрать (adapters §2).
- Для контрибьюторов: в `ci/check_layers.py` добавлено правило
  `install-path` (см. `LAYERS.md`).

### Обновление на 0.4.0 — ломающее изменение схемы

В 0.4.0 роль несёт не только `tier`, но и `effort`, а карта каналов получила
секцию `effort`. Установка версии 0.3.x и старше этих полей не содержит,
поэтому при обновлении **недостаточно** sha-сверки файлов:

- перерезолвить модель и усилие для КАЖДОГО агента всех установленных каналов
  и переписать соответствующие поля (`effort` во frontmatter claude-агентов,
  `model_reasoning_effort` в `.codex/agents/*.toml`);
- перегенерировать таблицу `{{AGENTS_TABLE}}` в `AGENTS.md` — у неё добавилась
  колонка `effort`;
- проверить, что ни у одного агента не проставлена верхняя ступень (`max`).

Это тот же класс операции, что и рендер-добавки адаптера: тела ролей не
трогаются, переприменяется рендер.

Заодно, если цель — git-репозиторий и `.gitattributes` в ней нет: положить
его из `project-template/gitattributes.example`, привести байты управляемых
файлов к конвенции (текст — LF, `*.ps1` — CRLF) и пересчитать sha. На
установках 0.3.x дерево обычно уже разъехалось, и без этого шага следующее
обновление упрётся в сплошное «изменено пользователем».

Если манифеста нет — обновление невозможно; допустима только переустановка с
предварительным бэкапом.

## Возврат практики в ядро

Практика, родившаяся в проекте, возвращается в дистрибутив так:

1. проходит входной фильтр (см. [`LAYERS.md`](LAYERS.md));
2. генерализуется — имена, пути и креды заменяются плейсхолдерами;
3. коммитится / оформляется PR в airules;
4. попадает в следующий релиз.

Проектный слой в дистрибутив **не возвращается никогда**.

## Опция: git subtree

Для тех, кто предпочитает вендоринг вместо инсталлятора, дистрибутив можно
подключить как `git subtree`: `git subtree add --prefix=airules <repo> <tag>
--squash`, обновление — `git subtree pull` на новый тег. Это осознанная
альтернатива, а не рекомендуемый путь: subtree не даёт манифеста, sha-сверки и
диалога о пользовательских правках, которые есть у инсталлятора.
