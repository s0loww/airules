# MCP-профиль 1С: фасад как единая точка входа

Документ установщика, а не правило: читается на шагах ONBOARD §1.1 (детект),
§2.4 (подтверждение инвентаря), §6 (рендер ролей) и §7 (MCP-конфиги) и в
целевой проект не копируется. Отвечает на один вопрос: **как выглядит
MCP-профиль 1С-проекта, когда на машине работает фасад**
(`services/1c-facade`), — и что из обычного детекта отдельных серверов при
этом отменяется.

Опыт, из которого профиль вырос: проект с прямыми серверами платформы в
`.mcp.json` получил роли, у которых в `tools:` были только эти серверы, — и
ни одна роль не могла позвать фасад, хотя сам проект был в нём
зарегистрирован. Профиль задаёт конфиг, текст роутинга и подстановку имён
инструментов **вместе**, потому что по отдельности они расходятся.

## 1. Когда профиль применяется

Оба условия, проверенные живьём на шаге детекта:

1. **Фасад отвечает.** Рукопожатие MCP (`initialize`, ONBOARD §4.3) по его
   адресу, и `tools/list` содержит глаголы `find`, `describe`, `docs`, `lint`.
   Адрес — у пользователя или из уже существующего конфига; не угадывать.
2. **Целевой проект зарегистрирован в реестре фасада.** `status` без
   аргументов перечисляет проекты; нужен тот, чей источник — выгрузка целевого
   проекта. Если его нет — профиль не применяется, пока пользователь не
   добавит проект в реестр фасада (это правка сервиса, не установки;
   эксплуатация — `services/1c-facade/RUNBOOK.md`).

Имя проекта в реестре фасада становится значением `<facade-project>` ниже.
Проект-расширение регистрируется **под своей базой** (реестр v2): тогда
`<facade-project>` — имя расширения, и каждый вызов по нему по умолчанию
захватывает и базу (`scope`).

Не выполнено хоть одно условие — обычный детект §1.1 без изменений.

## 2. `.mcp.json`

```json
{
  "mcpServers": {
    "1c-facade": {
      "type": "http",
      "url": "<адрес фасада>",
      "description": "Единая точка к 1С (проект <facade-project>): конфигурация, документация и ИТС, проверка кода, шаблоны. Только чтение (access: ro)."
    },
    "<сервер памяти>": { "...": "по ONBOARD §4.3, если подключается" }
  }
}
```

- **Прямые серверы, которые фасад покрывает, в конфиг не пишутся**: индексы
  кода и графа метаданных проекта, документация платформы, синтакс-анализатор,
  проверка кода, шаблоны. Они уходят в `DISABLED_MCP` с причиной «через
  фасад» — так следующая установка не вернёт их как «забытые».
- **`access: ro`.** Фасад не публикует мутирующих инструментов: генеративные
  правки кода и запись шаблонов намеренно не проброшены. Если реестр фасада
  на этой машине всё же публикует пишущий инструмент (`expose`) — сервер
  классифицируется `rw` по общему правилу ONBOARD §1.1.
- Сервер вне охвата фасада (например, база знаний БСП для конфигурации на
  БСП) остаётся отдельной записью, как при обычном детекте.

## 3. Текст роутинга в `AGENTS.md`

`{{MCP_ORDER}}` (тело контракта — по-английски):

```
one MCP entry point for 1C — `1c-facade` (<адрес фасада>, this project is
registered there as `<facade-project>`); its `coverage` block separates "no
such object" from "backend down" and marks a degraded answer. Configuration:
`find` (kind routine / metadata / form / text), `describe` (object dossier;
`<Объекты>.X.Форма.Y` — form layout plus its module; a module path or a
common-module name — the module structure), `calls`, `usages`, `status`.
Platform: `docs` (a name like `Объект.Метод` — exact article, prose — search
without a relevance threshold, `scope=its` — ITS, `version` — docs of that
platform version), `lint` (`mode=syntax` — fast analyzer gate, `check` /
`review` — model-backed correctness and style), `template`. Single-source
tools pass through one to one under `<backend>_<tool>` names. The index is
navigation, `<SOURCE_OF_TRUTH>` is the answer. Operational memory —
`<сервер памяти>` (see Layer boundary below)
```

Дополнения по фактам проекта, дописываются в ту же строку:

- **нет графа вызовов у проекта** (в `status` у проекта нет бэкенда `graph`):
  «`calls` is answered by the weaker code index and flagged — confirm call
  sites by search over `<SOURCE_OF_TRUTH>`»;
- **проект — расширение**: «calls default to the extension on top of its
  base; `scope=base|all|<extension>` picks explicitly; a base routine
  intercepted by an extension carries `overridden_by`».

`{{DISABLED_MCP}}` — перечень прямых серверов из п. 2 с причиной «reached
through the facade», плюс то, что фасад намеренно не публикует (генеративные
правки кода, запись шаблонов) — чтобы агент не искал обходной путь к ним.

## 4. Роли: allowlist и подстановка имён

**Allowlist.** Всем ролям, включая ro, — префикс сервера `mcp__1c-facade`
(layout §2: префикс — дефолт, инвентарь инструментов фасада известен).
Прямых серверов в `tools:` нет. Сервер памяти, если подключён, — не префиксом:
два его читающих инструмента поимённо, всем ролям (layout §2, исключение для
сервера памяти).

**Подстановка прозаических упоминаний** (layout §3) — по таблице:

| Категория в теле роли | Инструмент |
| --- | --- |
| поиск процедур по имени | `mcp__1c-facade__find` (`kind=routine`) |
| поиск кода по описанию | `mcp__1c-facade__find` (`kind=text`) |
| поиск объектов метаданных | `mcp__1c-facade__find` (`kind=metadata`) |
| поиск форм | `mcp__1c-facade__find` (`kind=form`) |
| досье объекта, структура модуля, раскладка формы | `mcp__1c-facade__describe` |
| граф вызовов | `mcp__1c-facade__calls` |
| использования, impact-анализ | `mcp__1c-facade__usages` |
| документация платформы, ИТС | `mcp__1c-facade__docs`; статья ИТС целиком — `mcp__1c-facade__codecheck_fetch_its` |
| проверка синтаксиса | `mcp__1c-facade__lint` (`mode=syntax`) |
| проверка корректности, ревью стиля | `mcp__1c-facade__lint` (`mode=check` / `review`) |
| шаблоны кода | `mcp__1c-facade__template` |
| вопрос Напарнику | `mcp__1c-facade__codecheck_ask_1c_ai` |
| проверка правилами проекта | `mcp__1c-facade__check` |
| состояние индексов | `mcp__1c-facade__status` |

Проброшенные имена (`<backend>_<tool>`) взять из живого `tools/list` фасада на
шаге детекта — у разных машин реестр публикует разное. Имя, которого в
`tools/list` нет, в роль не подставлять (layout §2: выдуманные имена запрещены).

Пометка «НЕ НАСТРОЕНО» про индекс метаданных в теле роли при применённом
профиле неверна: индекс есть, он за фасадом. Про отсутствие **графа вызовов**
— верна, если у проекта нет бэкенда `graph`; тогда в роль уходит формулировка
из п. 3.

## 5. Проверка после установки

- `.mcp.json` содержит фасад и (если подключён) сервер памяти — и больше
  ничего из охвата фасада.
- В `tools:` каждой роли есть `mcp__1c-facade`; ни одного прямого сервера из
  п. 2.
- Сервер памяти (если подключён) стоит в `tools:` ролей двумя инструментами
  поимённо — поиск и чтение; префикса сервера памяти нет ни у одной роли.
- В телах ролей нет имён прямых серверов (поиск по их именам пуст).
- Живой вызов `status` с `project=<facade-project>` отвечает, у бэкендов
  состояние `up`.

Фасад недоступен в момент работы — это пометка «канал не развёрнут» по общему
правилу ролей, а **не** повод вернуть прямые серверы в конфиг без решения
пользователя.
