# Документация 1С-конфигурации по коду

Скилл формализует конвейер, который однажды дал комплект из ≈40 docx и 30 схем по конфигурации
на ~1300 объектов: за один день, с проверкой каждого факта по коду. Суть — **главная сессия
не пишет документацию сама**, а ведёт её как выпускающий редактор: задаёт контракты, режет
работу на задания для агентов, проверяет их отчёты и держит сквозную согласованность.

Документация — производная от кода. Всё, что попадает в текст или на схему, должно опираться на
строку кода (`путь:строка`) или помечаться как непроверенный вывод. Это главное свойство
результата, ради него устроены все фазы.

## Что нужно на входе

- Выгрузка конфигурации в файлы (формат конфигуратора / EDT-экспорт XML) в git-репозитории.
- Node ≥ 18; для docx — пакет `docx`: один раз `npm ci` в `scripts/` скилла (без него генератор
  отвечает exit 2 и называет эту команду); для схем — скилл `archify` **с полями узла
  `link`/`description`** (в дистрибутиве airules он в комплекте; отдельно — форк
  `s0loww/diag_builder`, ветка `detail-link`: апстримный archify такие схемы не валидирует);
  для PNG — Chrome/Edge; для проверки docx — pwsh, опционально MS Word (open-check).
- Агенты — см. «Агенты и модели» ниже.

## Решения пользователя до старта (спросить, если не ясно из запроса)

Спрашивай только то, что реально меняет объём или форму. Типичные развилки:

1. **Охват**: вся конфигурация / одна подсистема или контур / вся, но один контур глубже.
   Это множитель объёма ×3–×10 — без ответа не начинать.
2. **Какое состояние кода** документировать: ветка/коммит. «Итоговое» часто не совпадает с
   текущей веткой рабочего дерева — проверь `git for-each-ref --sort=-committerdate` и
   `merge-base --is-ancestor`, предложи ветку-интегратор.
3. **Языки**: один или пара (ведущий + второй). Какой ведущий в именах блоков схем.
4. **Формат**: docx из генератора (рекомендуется — переиспользуемо и пересобираемо), Markdown,
   или оба.
5. **База сравнения** для статусов «новый / доработан / ядро»: коммит вендорской выгрузки
   (обычно первый коммит, добавивший `src`).

Остальное (состав документов, список схем, имена файлов) решай сам и сообщай.

## Фазы

Каждая фаза заканчивается проверяемым артефактом. Не переходи дальше «на доверии» к отчёту
агента — сверь ключевые числа сам (размеры, коды выхода, выборочно PNG/страницы).

### Фаза 0. Подготовка

1. Создай **отдельный worktree** нужной ветки только для чтения
   (`git worktree add --detach <path> <ref>`), чтобы не трогать рабочее дерево пользователя.
   Все агенты читают код только оттуда — впиши это в каждый контракт.
2. **Выясни состав репозитория** до первого контракта: что лежит в каждом каталоге выгрузки
   (основная конфигурация, расширения, их связь; `Configuration.xml` →
   `ConfigurationExtensionPurpose`, `NamePrefix`, `ObjectBelonging=Adopted`). Для **расширения**
   статус объектов — «собственный / заимствован» (inventory определяет режим сам), а не
   «новый / доработан / ядро» относительно вендорской базы. Ошибка здесь уходит во все контракты.
3. **Найди нормативные источники** контура: форматы обмена (XSD), нормативные документы, таблицы
   показателей/кодов в `docs/`. Они дают слой «соответствие норме» и метку `[N]` в фактах —
   без него документация объясняет *как*, но не *по какому правилу*.
4. Заполни конфиг комплекта по образцу `assets/docset.config.example.json`. Чек-лист: языки
   (один или пара), `source.baseline`, наборы (`sets[]`: каталог, префикс схем, заголовки),
   `sets[].internalDocs` (реестр дефектов — внутренний), `reference.base`, `clearCopy`. Имена
   файлов могут быть кириллическими. Сразу проверь: `make-nav.mjs --config <cfg> --dry-run`.
5. Создай выходной каталог: `_facts/`, `_build/`, `_png/`, по подкаталогу на каждый набор.
6. **Проба оформления схемы** (5 минут, экономит часы): собери крошечную схему на 3 узла в
   нужном языковом режиме, посмотри PNG. Для двух языков: `label` — ведущий язык, `sublabel`
   (мелкий шрифт) — второй; подписи рёбер `A · Б` требуют большего зазора между узлами.

### Фаза 1. Инвентаризация (скрипт, не агенты)

`node scripts/inventory.mjs --config <cfg>` → `inventory.json` + `inventory-summary.md`: все
объекты, синонимы по языкам, реквизиты, ТЧ, движения документов, состав подсистем, статус
относительно базы (для расширения — принадлежность own/adopted). Проверь код выхода (не через
`| tail` — пайп его теряет) и сводку глазами: совпадение числа объектов с числом XML по папкам,
выборочно 3–5 объектов против XML. Справочник объектов можно собрать сразу:
`node scripts/docgen/reference.mjs --config <cfg>`. Тут же `node scripts/callgraph.mjs --config <cfg>` →
`_facts/callgraph.json` + `callgraph-summary.md`: места вызова экспортных методов, значения перечислений
и константы без ссылок — вход аналитикам («вызывается» подтверждается местом вызова) и реестру 91.

**Проверь статусы на шум.** Если «доработан» получилось у большинства объектов — почти наверняка
массовый коммит переводов/переэкспорта. Найди его (`git show --stat`), включи нормализацию
(`normalizeTranslations`). Нормальная картина — «доработано» 5–20 % объектов. Шумный статус
отравит теги на всех схемах и потом придётся делать отдельный проход.

### Фаза 2. Факт-файлы (аналитики, параллельно)

Нарежь конфигурацию на участки (см. `references/doc-plan.md`): учётную — по подсистемам
(6–10 участков), технический/интеграционный контур — по стадиям конвейера (3–5 участков). Один
агент на участок, самая сильная модель — это фундамент всего. Если в репозитории уже есть
документация проекта, аналитики читают её только как `[D]` и никогда не переписывают —
иначе ошибки старых текстов (часто это пересказ устаревших комментариев) уйдут в новые. Контракт — `references/fact-contract.md`,
шаблон задания — `references/prompts/analyst.md`. Положи контракт файлом в `_facts/_SPEC.md`,
в задание — только путь к нему и границы участка.

Факт-файл: назначение, процессы пошагово, ключевые объекты, движения документ → регистр, отчёты,
интеграции, роли, **особенности и дефекты**, предложения схем, открытые вопросы. Всё с
`путь:строка` и метками `[V]` проверено по коду / `[D]` из документа проекта / `[I]` вывод.

По мере прихода отчётов собирай в заметку сессии список находок — это станет реестром
ограничений и итоговым отчётом пользователю.

### Фаза 3. Реестры и контракты вывода

Когда факт-файлы готовы (можно раньше — по мере прихода):

- Реши **состав документов и схем** и зафиксируй **имена файлов** в `_REGISTRY.md` каждого набора
  (схемы) и в списке документов. Имена нужны всем следующим агентам для перекрёстных ссылок —
  без них авторы пишут «см. документ по продажам» словами, и это потом чинит редактор.
- Положи `references/diagram-contract.md` → `_build/DIAGRAM_SPEC.md` и
  `references/writer-contract.md` → `_build/WRITER_SPEC.md`, подставив пути, языки, коммит.
- Зафиксируй **ключевые термины** (особенно там, где синонимы конфигурации неудачны) — короткий
  список в WRITER_SPEC. Иначе авторы и схемы разойдутся в терминах (так было: «тальманская
  ведомость» против «приёмочная ведомость» — понадобился отдельный проход).

### Фаза 4. Схемы (агенты, параллельно)

Один агент — одна-две схемы одного участка. Шаблон — `references/prompts/diagram.md`. Корневая
схема набора (`*-00-panorama`) ссылается на все остальные. Приёмка каждой: archify `validate
--quality showcase` 9/9 без ошибок и предупреждений → `deliver` → `visual-check` → агент
смотрит PNG. После схем: `node scripts/export-png.mjs --config <cfg>` → чистые PNG для docx.

### Фаза 5. Генератор документов

`scripts/docgen/`: один JSON содержания → docx на каждый язык (`CONTENT_FORMAT.md`). Справочник
объектов генерируется из инвентаризации: `node scripts/docgen/reference.mjs --config <cfg>` (свойства
подписок, заданий, констант, общих модулей — сами; колонка «Назначение» — из `_facts/purposes.json`
аналитиков, если он есть). Пробные сборки — с `--out <scratch>`: отчёт ложится туда же.
Если скрипты уже на месте — фаза сводится к `npm i` и пробной сборке `_sample.json`.

### Фаза 6. Тексты (авторы, параллельно)

Один автор — один документ. Шаблон — `references/prompts/writer.md`. Типовой комплект: состав
комплекта (00), общая архитектура (01), по документу на участок, обзор особого контура,
справочник объектов (90, генерируется), реестр ограничений (91, внутренний), глоссарий (92).
Для особого контура — отдельный подробный набор. Авторы собирают docx во временный каталог и
прогоняют `verify-docx`; в боевые каталоги собирает только оркестратор. Поле `png` авторы не
ставят — картинки подставляются на финале.

Реестр 91 и глоссарий 92 пишутся из **всех** факт-файлов — запускай их, когда факты готовы.
Состав комплекта 00 — строго после завершения всех остальных текстов, и его таблицы
генерируются скриптом из готовых JSON: на финале генератор 00 перезапускается в любом случае.

### Фаза 7. Согласование (редакторы и проходы)

Разные авторы → расхождения. Обязательные проходы (шаблоны в `references/prompts/`):

1. **Редактор на набор** (`editor.md`): явные ссылки между документами по реестру имён,
   термины по глоссарию, одинаковые числа и формулировки ключевых фактов, дополнение реестра 91
   находками, которые авторы нашли уже в своих разделах (так всплывают самые ценные).
2. **Проход по схемам** (`sweep.md`), если за время работы изменились статусы или термины:
   теги статуса по исправленной инвентаризации, термины как в текстах. Каждая изменённая схема —
   снова полная приёмка.
3. Ошибки, найденные одним редактором в зоне другого, пересылай ему сообщением, а не правь сам.

### Фаза 8. Финальная сборка и приёмка

Один агент по шаблону `references/prompts/final.md`: сквозной `validate`+`check` всех схем и
сверка HTML с JSON (повторный `deliver` во временный путь и сравнение), `check-lifecycle.mjs`
(состояния lifecycle-схем = значения перечисления, риски помечены), свежий экспорт PNG,
вставка `png` в блоки схем (`fill-png.mjs`), сборка всех docx в боевые каталоги, `verify-docx` всех,
open-check в Word (`-OutDir` — PDF во временный каталог), просмотр 2–3 страниц PDF, `make-nav.mjs`
(index.html + README с контрольными суммами, ноль битых ссылок), экспортная копия `make-clear.mjs`
(только index + html + docx, **без `internalDocs`** по умолчанию — index копии перерисован без них;
ссылки проверены внутри копии, включая ссылки docx на исключённые документы).

После — отчёт пользователю: что собрано, где лежит, чем проверено, **главные находки по коду**
(безопасность и высокая серьёзность — первыми, с пометкой, что подтверждено кодом, а что вывод),
что осталось за пользователем (коммит, внутренние документы в экспортной копии, рабочий worktree).
Не коммить без явного запроса; если коммитить — в отдельную ветку, не в чужую рабочую.

## Роль оркестратора — как держать качество

- **Контракт файлом, задание коротко.** Общие правила — в `_SPEC.md`/`DIAGRAM_SPEC.md`/
  `WRITER_SPEC.md`, задание агента — ссылка на контракт + границы + выход + чем проверить.
  Контракт правится один раз — все следующие агенты получают исправление.
- **Каждое «готово» подтверждено выводом команды** (коды выхода, 9/9, sha256), а не словами.
  Числа из отчётов сверяй выборочно сам — однажды в отчёте перепутались суммы спецификации.
- **Код побеждает документы проекта.** Расхождения план ↔ код — ценная находка: фиксируй в §8
  факт-файла и в реестре, на схеме показывай код.
- **Находки агентов собирай по ходу** и сообщай пользователю короткими строками — у него
  появляются вопросы и решения (например, «следующей фазой — подробный комплект по контуру X»).
- **Лимит параллельных агентов** (часто 20): держи очередь и запускай по освобождении мест.
- **Не экономь на модели для фактов и текстов**; механику (перенос, проверки) можно дешевле.

Список граблей с лечением — `references/lessons.md`. Прочитай его до фазы 2: большая часть
проблем прошлого запуска предсказуема.

## Агенты и модели

Скилл — **осознанный веер агентов** (десятки запусков). Запускай его только по явному запросу
пользователя собрать или обновить комплект; в правилах экономии оркестратора (делегирование —
исключение) это и есть такое исключение, названное пользователем.

Если в проекте есть определения ролей (дистрибутив airules — `.claude/agents/`), задания идут
**проектным ролям**, а не встроенным универсальным агентам: встроенные (`general-purpose`,
`Explore`) не видят промпт роли и её набор MCP — поиска по коду проекта у них нет.

| Фаза | Роль airules (оверлей 1С) | Почему |
|---|---|---|
| 2 — факт-файлы, 4 — схемы, 6–7 — тексты, реестры, редактура, 8 — финал | `1c-analytic-deep` | каждый шаблон задания требует сильную модель: факты с сырого кода, раскладка схем, естественный текст на двух языках, строгая приёмка. Не `1c-doc-writer` — его тир low |
| проход по схемам (`sweep.md`) — теги и термины по готовому списку | `1c-analytic` | механическая правка по готовым данным |

Ролей нет — универсальный агент с сильной моделью. Отдельная рабочая копия ветки (фаза 0) —
только для чтения; в airules она же покрывает требование правила `preflight-worktree`.
