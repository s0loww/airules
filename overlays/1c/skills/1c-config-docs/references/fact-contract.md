# Спецификация фактов для документации

Этот файл — общий контракт для аналитиков, которые собирают факты о конфигурации. По фактам
потом пишутся документы и схемы. Факт-файл — рабочий материал: полнота и точность важнее стиля.

## Источник

- **Авторитетный код:** `<worktree>\<srcRoot>` — рабочая копия ветки `<ref>` (коммит `<head>`).
  Только чтение. НЕ читать `<repo>\<srcRoot>` — там может быть другая ветка.
- Документы проекта (в той же рабочей копии): `<пути к архитектуре, openspec, реестрам дефектов,
  нормативке>`. Если документ противоречит коду — прав код; расхождение записать в §8.
- MCP-поиск по коду можно использовать, но его индекс может быть построен по другой ветке:
  всё найденное подтвердить файлом из рабочей копии.
- Устаревшие/заброшенные подсистемы описать кратко: что в них есть и используется ли.

## Язык и имена

- Факт-файл пишется на `<язык оркестратора>`. Идентификаторы 1С — точно как в коде.
- Для каждого значимого объекта и процесса давать имя на каждом языке комплекта (синоним
  соответствующего языка; при отсутствии — `<fallback>`); если синонима нет — предложить
  перевод и пометить `[перевод]`. Неудачные синонимы конфигурации отмечать.
- Бухгалтерские термины: «Post» = провести / contabilizar (не «publicar»).

## Ссылки и метки достоверности

- Каждое утверждение о логике — со ссылкой `путь:строка` относительно `<srcRoot>`
  (например `Documents/Tarja/Ext/ObjectModule.bsl:120-164`).
- Метки: `[V]` — проверено по коду; `[D]` — из документа проекта (указать какого);
  `[N]` — из нормы/формата (XSD, нормативный документ, таблица кодов; указать источник);
  `[I]` — вывод аналитика. Не выдумывать: нет факта — так и написать.
- **Утверждения о вызовах и порядке** («вызывается», «используется», «не используется»,
  «сначала X, затем Y», «подключено») получают `[V]` только со ссылкой на **место вызова**
  (или на результат поиска всех вызовов), а не на определение функции и не на комментарий.
  Комментарии и шапки модулей часто устарели — это самая частая причина ошибок в документации.
- Существующую документацию проекта читать только как `[D]` и никогда не переписывать.

## Формат `<outputRoot>/_facts/<NN>-<имя>.md`

```
# <Подсистема(ы)> — факты
Охват: какие подсистемы / группы объектов. Коммит: <head>.

## 1. Назначение
2–6 абзацев: что делает этот участок учёта, для кого, как связан с остальными.

## 2. Процессы
### 2.N <Имя на языке 1> / <Имя на языке 2>
- Кто и когда запускает; входные данные.
- Шаги: документ → проверка → проведение → что меняется (регистры, движения, статусы).
- Результат: отчёты, печатные формы, выгрузки, э-документы.
- Правила и проверки (заполнение, блокировки, контроль остатков, запреты).
- Ссылки на код.

## 3. Ключевые объекты
Таблица: Вид | Имя 1С | имя яз.1 | имя яз.2 | Назначение (1 строка) | Ключевая логика / ссылка.
Только значимые (≈ 10–40 на участок). Полный перечень даёт инвентаризация.

## 4. Движения: документ → регистры
Таблица: Документ | Регистр | Вид движения / что пишет | Условие | Ссылка.
Отдельно отметить расхождения «регистр в RegisterRecords, но код его не пишет» и наоборот.

## 5. Отчёты и печатные формы
Таблица: Имя | имена | Что показывает | Источник данных (регистры).

## 6. Интеграции, регламентные задания, подписки, обмены, веб-сервисы
Для каждой внешней точки — куда уходят данные (адрес из кода), что именно уходит.

## 7. Роли и функциональные опции участка
Матрица прав по `Roles/*/Ext/Rights.xml`; где проверка роли только в форме, а не в модуле объекта.

## 8. Особенности, ограничения, известные дефекты
Унаследованное поведение, грабли, дефекты из реестров проекта, расхождения документов с кодом.
Для каждого: что, последствие, [V]/[I], ссылка.

## 8а. Соответствие норме (если у участка есть норма/формат)
Какие требования нормы участок реализует, где (`путь:строка`), чего нет или что сделано иначе;
метка `[N]` у каждого требования.

## 9. Предложения для схем
2–4 схемы archify: тип (architecture / workflow / sequence / dataflow / lifecycle), что
показывает, список узлов (≤ 12, имена на языках комплекта), главный путь.
```

## Объём

Лучше полный и точный файл на 60–120 КБ, чем короткий. Не пересказывать код построчно:
описывать логику так, чтобы по ней можно было написать руководство для бухгалтера и для
разработчика. Ничего не менять в репозитории, кроме своего факт-файла. Не коммитить.
Временные файлы — только в своей подпапке scratch (параллельные агенты делят одну папку).
