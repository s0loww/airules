# Контракт авторов документов

Автор пишет ОДИН файл содержания — JSON в формате генератора. Из него собираются
`<base>_<suffixP>.docx` и `<base>_<suffixS>.docx`. Оба языка — полноценные, равные по содержанию
тексты, а не подстрочник.

## Что прочитать

1. `<scripts>\docgen\CONTENT_FORMAT.md` — формат (блоки, значения `{<P>, <S>}`, inline-разметка
   `` `code` ``, `**bold**`, `[текст](url)` — у каждого языка своя ссылка), валидация. Образец —
   `<scripts>\docgen\examples\_sample.json`.
2. Свои факт-файлы `<outputRoot>\_facts\NN-*.md` (ссылки на код `<worktree>\<srcRoot>`, метки
   [V]/[D]/[I]). При сомнении — открыть код. Писать о КОДЕ, не о плане.
3. Реестры схем `<set>\_REGISTRY.md` и **список имён документов комплекта** (ниже) — для ссылок.
   Готовые схемы `*.json` — их описания проверены по коду и могут уточнять факт-файл.
4. Имена объектов: `_facts\inventory.json`. Полный справочник — документ `<90_…>`: ссылаться,
   не дублировать.

## Документы комплекта (имена файлов для ссылок)

<таблица: набор | каталог | base | тема>. Ссылка из текста на `P` — `[base](base_<suffixP>.docx)`,
на `S` — `[base](base_<suffixS>.docx)`; в другой набор — относительный путь (`../`, `<dir>/`).

## Ключевые термины

<список: термин P — термин S — пояснение; особенно где синоним конфигурации неудачен>.
Отклоняться нельзя без причины: разные авторы иначе разъедутся.

## Аудитория и тон

Пользователь-бухгалтер и разработчик/внедренец. Объяснять логику работы: что делает участок,
как идут процессы, что пишет каждый документ, какие правила и проверки, где грабли. Не
пересказывать код построчно.

- `P` — деловой язык с местной профессиональной терминологией. «Post» = <провести / contabilizar>.
- `S` — нормальный технический язык, термины 1С; реалии `P` — в скобках при первом упоминании.
- Идентификаторы 1С — в `` `code` ``, точно как в коде; при первом упоминании — синоним на языке
  текста.
- Метки [V]/[D]/[I] и `путь:строка` в основной текст НЕ выносить. Выводы [I] — осторожно:
  «según el código, … (a verificar)» / «по коду … (требует проверки)».
- Секреты (PIN-коды лицензий, пароли, токены, учётные данные из кода) в документацию не писать —
  только факт их наличия.
- Ключевые ссылки на код — последним разделом «Ссылки на код» (таблица тема | путь:строка,
  10–30 строк).

## Структура документа участка (адаптировать)

1. `toc`
1а. Коротко — 1–1,5 страницы: что делает участок, главный путь, 3 главные особенности
   (для читателя, которому не нужны подробности)
2. Назначение и охват
3. Понятия и справочные данные
4. Процессы — по каждому: назначение, кто и когда, шаги, что проводится, правила и проверки,
   результат. Перед процессом со схемой — блок `diagram`.
5. Ключевые объекты — таблица (Объект 1С mono | имя | назначение).
6. Движения — таблица документ → регистр → что пишет.
7. Отчёты и печатные формы.
8. Интеграции, регламентные, роли, ФО.
9. Особенности и ограничения — главное; полный реестр — документ `<91_…>`.
10. Ссылки на код.

## Блоки `diagram`

- `href` — относительно выходного docx (свой набор: `bn-07-….html`; другой: `../bl-04-….html`
  или `<dir>/bn-….html`).
- **Поле `png` не задавать** — картинки подставит оркестратор после экспорта. `caption` на
  языках комплекта: что показывает схема.

## Файл, проверка, отчёт

- Путь: `<contentDir>\<id>.json` (id и base задаёт задание); принадлежность набору — поле `set`
  (или `outDir`).
- Проверка (обязательно, из `<scripts>`):
  `node docgen/build.mjs --config <cfg> <contentDir>/<id>.json --out <scratch>\docs-<id>` → exit 0;
  затем `pwsh -NoProfile -Command "& ./docgen/verify-docx.ps1 -Path '<a.docx>','<b.docx>' -Report '<scratch>\<id>-verify.json'"`
  → exit 0. Предупреждения «href target not found» при сборке во временный каталог ожидаемы.
- Не собирать в боевые каталоги (это делает оркестратор), не трогать чужие файлы, не коммитить.
- Отчёт: путь JSON, размер, число блоков/разделов/таблиц, итог build и verify (фактический
  вывод), какие факты не подтвердились кодом, что осталось под вопросом, **новые находки
  дефектов** (их оркестратор перенесёт в реестр ограничений).
