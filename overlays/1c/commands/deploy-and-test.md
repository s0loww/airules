# Деплой и проверка (1С)

Команда-каркас: конкретные пути, имена баз, версию платформы и имя расширения
даёт **проектный слой** (корневой контракт проекта / проектная копия этой
команды). Здесь — порядок и жёсткие правила, одинаковые для любого 1С-проекта.

## Жёсткие правила

- **Определи, что лежит в каталоге исходников: конфигурация или расширение**
  (`Configuration.xml` → `Properties/Name`; сверься с проектным слоем). Если это
  РАСШИРЕНИЕ — каждый `1cv8 DESIGNER /LoadConfigFromFiles` и `/UpdateDBCfg`
  ОБЯЗАН нести `-Extension <ИмяРасширения>`, а каждый `ibcmd infobase config
  import` / `apply` — `--extension=<ИмяРасширения>`: голая команда без него
  **перезапишет основную конфигурацию базы**. Сомневаешься — не запускай сырые
  команды, используй проектный скрипт деплоя.
- **Деплой только проектным инструментом** (скрипт деплоя, указанный в
  проектном слое), не сырыми командами платформы: скрипт несёт правильные
  флаги, режимы Load/Update и редакцию пароля в логах.
- **Целевая база — тестовая**, из env-профиля проекта (секция указана в
  проектном слое). Боевые базы не трогать без явного указания пользователя.
  Креды не выводить ни в stdout, ни в логи, ни в отчёты; env-файл не
  редактировать.
- Версия платформы — фиксированная в проектном слое; не подставлять «какая
  найдётся». Для копии стенда — ровно сборка стенда.
- **Локальная база или база под кластером.** Локальную тестовую базу можно
  собирать и обновлять `ibcmd` и поднимать `ibsrv` (скилл `ibcmd-ibsrv`).
  База под кластером серверов (командный dev, тестовый контур) — только
  штатным путём через кластер; `ibcmd`/`ibsrv` напрямую в её СУБД не ходят.

## Порядок

1. **Деплой** проектным скриптом → проверить exit-коды/лог (успех загрузки И
   успех обновления структуры БД). Изменения структуры (новые ТЧ/реквизиты)
   требуют монопольного обновления вместо динамического. Службы, держащие
   сеансы базы (публикация, HTTP-мост, `ibsrv`), останавливает и поднимает сам
   скрипт деплоя. Затем **проба**: новые объекты и реквизиты существуют в базе,
   `/CheckModules` по нужным контекстам чист — exit 0 загрузки не
   доказательство (`rules/testing-1c.md`). Вердикт любого пакетного запуска —
   три сигнала: код выхода, `/DumpResult` = `0`, чистый `/Out`
   (`rules/getconfigfiles.md` → Step 3).
2. **Статическая проверка** (BSL LS / проектный analyze-контур, если настроен):
   у зрелых проектов есть baseline диагностик — **гейтить только новые**
   относительно baseline, старые не чинить без отдельной задачи.
3. **Проверка после деплоя** — каналами, которые реально настроены в проекте
   (см. проектный слой), по модели слоёв `rules/test-model.md` и в порядке
   каналов роли тестировщика; в порядке дешевизны:
   - смоук клиентом: поднять клиент на тестовой ИБ, дождаться отклика; после
     проверки клиент закрыть (открытый клиент со старой версией расширения
     ломает последующие COM-подключения к файловой базе);
   - прогон юнит-контура без интерфейса (`/C`-раннер или YaXUnit), если есть;
   - проверка данных/движений регистров через HTTP-мост к базе или
     COM-скриптами по COM-контракту проекта (изменяющие скрипты — только с
     согласия пользователя и только в копиях);
   - сценарные прогоны (Vanessa/vrunner), если suite настроен — для
     1С-контура это и есть «affected automated tests» гейта D
     `rules/verification-matrix.md`;
   - MCP-доступ к базе (OneMCP и т.п.), если развёрнут на тестовой ИБ.
   Каналы, которых в проекте нет (веб-публикация, раннеры), — не выдумывать и
   не имитировать: явно сказать, что канал не развёрнут.

## Отчёт

Exit-коды деплоя · результат пробы после деплоя · новые Error статпроверки ·
результат каждой проверки PASS/FAIL с доказательством (лог/запрос/скриншот),
у каждого прогона — свой артефакт, не перезаписанный следующим · сравнение с
baseline, а не голый счёт · точные тексты ошибок. Прерванный прогон (массовые
ошибки канала, перезагрузка) — «прерван», а не FAIL.
