# Preserve a reusable method

Start from an observed result: task class, prerequisites, decisive action,
outcome and a non-sensitive evidence reference. An unresolved workaround is a
limitation, not a procedure. Ordinary activity or a long tool trace alone does
not justify a new skill.

## Find the owner

Inspect the actual skill index and nearest matching skill before adding a name.
Keep one maintained explanation: reuse what already fits, patch the affected
step when it nearly fits, and create a skill only for a distinct reusable gap.

Separate the destinations:

- A transferable procedure belongs in a skill.
- A stable project decision follows the project's `decisions-log` policy.
- A diagnosed recurring failure found by its symptom follows `case-book`.
- A proposed change to standing behavior or permissions belongs to its rule
  owner; it is not hidden in a skill as a workaround.

Resolve these owners through the project's instruction index when present.
Use the authorized source package for managed content, not generated copies or
vendor caches. Resolve a writable destination from the host's real discovery
configuration; a file in an arbitrary folder is not an installed skill. Prefer
project scope for project-specific methods. A useful lesson does not authorize
unrelated global configuration, publication or software installation.

## Make the smallest useful change

Read the current target and preserve concurrent edits. Write a short YAML `name`
and a discriminating `description` stating the task and trigger. Keep the body
focused on prerequisites, the action that changes the outcome, its observed
pitfall and a success check. Preserve supported metadata on updates.

Keep incident transcripts, credentials, local account details and repeated policy
out of the skill. Put substantial conditional material in topic-named references,
linked from the step that needs it. Add an executable helper only for reusable
deterministic work, and exercise its relevant check before presenting it as ready.
Use actual available tools; examples from another host do not register commands.

## Validate the changed behavior

Check frontmatter and local resource links. For a materially changed procedure or
trigger, use a small isolated task exercising it and a nearby non-match where
misrouting matters. Inspect the resulting actions/artifact, not a confidence
claim. Do not repeat a costly live operation merely to test instruction wording.

Report the source path, change and evidence. Use the host's supported refresh or
next-session discovery and distinguish written, discoverable and activated states.
Record a durable outcome through the existing memory owner only when it adds new
information. A successful reuse with no finding needs no rewrite.
