# Канальные адаптеры — как раскладывать дистрибутив по каналам

Источник контента один: `core/` (+ `overlays/<stack>/`, если стек подтверждён на установке).
Адаптер ничего не добавляет к содержанию — он описывает только КУДА и в каком ФОРМАТЕ
инсталлятор раскладывает этот единственный источник под конкретный канал. Ставятся только
каналы, выбранные на установке (см. процедуру ONBOARD, §2.1) — адаптер для невыбранного
канала не применяется вообще.

Резолв модели агента для любого канала: `tier` роли (`core/agents/ROLES.md`) → канал в
`core/channels/model-map.yaml` → значение по tier. Общая процедура — в конце файла.

---

## plain (ставится всегда)

Агенто-агностичный базовый слой. Работает для любого агента, в том числе не перечисленного
явно (сторонние и нишевые агенты, любые CLI-обвязки без собственного формата).

- `AGENTS.md` — корневой контракт в корень репозитория.
- `rules/` — корневой каталог с телами правил (`core/rules/*` + `overlays/<stack>/rules/*`,
  если стек подтверждён).
- `openspec/` — в корень.
- Роли — не отдельными файлами, а секцией внутри `AGENTS.md`: роль, tier, модель из
  `other`-маппинга `model-map.yaml` (плейсхолдеры `{{MODEL_*}}`, если пользователь их не
  заполнил на установке).
- MCP — текстом внутри `AGENTS.md` (порядок инструментов, что исключено), без машиночитаемого
  конфига: агент, у которого нет своего формата подключения инструментов, обязан прочитать это
  как обычный текст контракта.

## claude (Claude Code)

- `CLAUDE.md` — ровно одна строка: `See @AGENTS.md`.

  **⚠ Грабля:** без символа `@` Claude Code не распознаёт директиву импорта — файл не
  подтягивается, контракт молча не загружается, и агент работает без него, не сообщая об
  ошибке.

- Правила — только корневой `rules/` (как в plain). Каталог `.claude/rules/` под эти правила
  не используется и не создаётся.

  **⚠ Грабля:** тела правил нельзя класть в `.claude/rules/` — Claude Code индексирует всё
  содержимое этого каталога как always-on контекст (подгружается в каждый промпт целиком,
  порядка десятков тысяч токенов на полный набор правил), что убивает ленивую по-требованию
  загрузку, на которой строится вся структура дистрибутива. Каталог `.claude/rules/` не
  должен существовать в раскладке вообще.

- `.claude/agents/<role>.md` — один файл на роль:
  - frontmatter: `name`, `description`, `model`, `tools`, `allowParallel`;
  - `model` — резолвится из `claude`-ветки `model-map.yaml` по tier роли (см. общую процедуру
    резолва модели ниже); override-tier `fast` в `claude`-ветке не определён, поэтому роли с
    `override: fast` получают свой базовый tier;
  - `tools` — псевдо-значения `ro`/`rw` из `ROLES.md` разворачиваются в реальные имена
    инструментов канала: `ro` → `["Read", "Grep", "Glob"]` + MCP-инструменты, объявленные для
    проекта на установке; `rw` → тот же набор плюс `["Write", "Edit", "Bash"]`.

  **⚠ Грабля:** псевдоимена вида `Shell`/`MCP` в allowlist инструментов Claude Code не
  распознаются — список обязан состоять из настоящих имён инструментов канала (`Bash`, а не
  `Shell`; конкретные `mcp__<server>__<tool>`, а не общее слово `MCP`).

- `.claude/skills/<skill>/` — копия из `core/skills/<skill>/` (+ оверлейные skills, если стек
  подтверждён).

- **Опционально: прокси сжатия вывода команд (rtk)** — если пользователь применяет
  `core/rules/tool-output-economy.md` глубже, чем явные `rtk`-префиксы, канал позволяет
  автоперехват через PreToolUse-hook (`rtk init -g` — ставит только сам пользователь;
  инсталлятор дистрибутива хуки НЕ создаёт и НЕ меняет).

  **⚠ Грабля:** hook перехватывает только вызовы инструмента Bash — встроенные Read/Grep/Glob
  через него не проходят и не переписываются; экономия на них достигается только явными
  `rtk read`/`rtk grep`-вызовами по правилу. Второй нюанс: `rtk ls`/`tree` требуют coreutils
  в PATH (в bash-сессии есть, в чистом PowerShell — нет; там пользоваться raw-командами).
- `.claude/commands/*.md` — копия из `core/commands/*.md`.
- `.mcp.json` — корень: `{ "mcpServers": { … } }`, один блок на сервер из декларации MCP
  проекта.

  **⚠ Грабля:** у серверов, доступных по сети (не через локальный процесс), обязательно поле
  `"type": "http"`. Без него Claude Code по умолчанию считает сервер локальным процессом,
  ищет поле `command`, не находит и молча пропускает сервер при старте — никакой ошибки в
  интерфейсе не будет, сервер просто не появится в списке подключённых.

## codex (Codex CLI)

- `.codex/agents/<role>.toml` — один файл на роль. Полный шаблон (в донорских материалах
  канала он отсутствовал, поэтому фиксируется явно):

  ```toml
  name = "<role>"
  description = "<когда звать>"
  model = "<model-map: codex.<tier>.model>"
  model_reasoning_effort = "<model-map: codex.<tier>.reasoning>"
  developer_instructions = '''
  <инструкции роли; многострочный текст>
  '''
  ```

  **⚠ Грабля:** если `developer_instructions` содержит абсолютные пути Windows с обратными
  слэшами (диск с большой буквы вида `Х:\Папка\...`), использовать только литеральный
  многострочный блок `'''…'''`. Базовый (интерполирующий) блок `"""…"""` разбирает `\U` и
  `\P` — начальные буквы таких путей — как экранирующие последовательности → парсер TOML
  падает на «Invalid hex value» → codex молча выбрасывает роль целиком из загрузки
  (диагностируется командой `codex doctor`, которая покажет
  «Ignoring malformed agent role definition» — без этой команды сбой останется незамеченным).

- `.codex/rules/` — зеркало `rules/` (если адаптер канала так настроен) либо общий корневой
  `rules/` без дублирования; `.codex/skills/` — копия `core/skills/` (+ оверлейные).
- `.codex/config.toml` — секция `[mcp_servers.<name>]` на каждый сервер.

  **⚠ Грабля:** codex мёрджит глобальный `~/.codex/config.toml` с проектным конфигом. Если
  сервер с тем же именем в глобальном конфиге объявлен как локальный процесс, а проектный
  конфиг пытается переопределить его на сетевой адрес (`url`), запуск падает с «url is not
  supported for stdio» и codex не стартует вовсе. Перед генерацией `.codex/config.toml`
  инсталлятор обязан прочитать глобальный конфиг пользователя и исключить из проектной
  раскладки серверы, которые там уже объявлены с конфликтующим транспортом.

- Эскалация reasoning-усилия: максимальный tier канала выставляется только вручную, по
  явному решению на конкретную сложную задачу (см. пометку в `model-map.yaml`) — в `.toml`
  всегда записывается значение из карты по tier роли, не максимум канала.

## cursor

- `.cursor/rules/<name>.mdc` — зеркало каждого файла `rules/`; frontmatter ровно:

  ```yaml
  ---
  description: "<...>"
  alwaysApply: false
  ---
  ```

  **⚠ Грабля:** без `alwaysApply: false` cursor может подхватить правило как always-on —
  контракт ленивой по-требованию загрузки для этого правила теряется, оно попадает в контекст
  каждого промпта независимо от релевантности.

- `.cursor/agents/<role>.md` — один файл на роль, модель резолвится из `cursor`-ветки
  `model-map.yaml` (по умолчанию — плейсхолдеры, запрашиваются у пользователя на установке).
- `.cursor/mcp.json` — `{ "mcpServers": { … } }`, обычно без поля `"type"` — cursor
  толерантен к его отсутствию.

## Общие процедуры

### 1. Резолв модели

1. Взять `tier` роли из `core/agents/ROLES.md`.
2. Найти значение по адресу `channels.<канал>.<tier>` в `core/channels/model-map.yaml`.
3. Если роль несёт `override: fast` и канал определяет tier `fast` — использовать его вместо
   базового tier; если канал `fast` не определяет — оставить базовый tier роли (см. семантику
   override в `ROLES.md`).
4. Если итоговое значение — плейсхолдер `{{...}}`, подставить ответ, полученный от
   пользователя на установке.
5. Записать результат в agent definition в формате канала (frontmatter-поле, `.toml`-поле или
   текстовая секция `AGENTS.md` — в зависимости от канала).

### 2. Маппинг tools

| псевдо-значение (`ROLES.md`) | claude | codex | cursor |
| --- | --- | --- | --- |
| `ro` | `["Read", "Grep", "Glob"]` + проектные MCP-инструменты | не разворачивается в allowlist — доступ ограничивается текстом инструкций роли (своей модели прав codex не имеет) | описывается словами в теле роли — формат агента cursor не требует отдельного списка инструментов |
| `rw` | `ro` + `["Write", "Edit", "Bash"]` | то же — ограничение через инструкции, не через список инструментов | то же — словами в теле роли |

Для codex и cursor `ro`/`rw` не превращаются в машиночитаемый allowlist — ограничение
провозится в тексте роли (`developer_instructions` / теле `.md`); это единственная опора,
которая у этих каналов есть.

**Allowlist MCP по префиксу сервера.** Инвентарь инструментов сервера оффлайн недоступен
(перечень `mcp__<server>__<tool>` можно узнать только у живого сервера), поэтому в allowlist
агентов ДОПУСТИМ и является дефолтом префикс сервера целиком: `mcp__<server>` (= все
инструменты этого сервера). Перечислять конкретные `mcp__<server>__<tool>` — только когда
инвентарь достоверно известен (живое подключение или инвентарь, поставляемый с профилем
проекта). Выдуманные имена инструментов запрещены. Имя сервера в префиксе — каноническое
(см. нормализацию имён в ONBOARD §7).

### 3. Инстанцирование инструментальных упоминаний

Тела агентов и правил ссылаются на инструменты обобщённо (прозаически, например «инструменты
поиска по коду проекта»). При раскладке под конкретный проект инсталлятор обязан заменить
такие прозаические упоминания на конкретные имена MCP-инструментов, обнаруженные на шаге
детекта проекта (см. процедуру ONBOARD), и подтвердить подстановку на шаге верификации
ONBOARD — прозаическая формулировка в разложенном агенте является признаком незавершённой
установки.

### 4. Блок «Дисциплина исполнения» (добавляется при рендере каждому агенту)

При раскладке под любой канал инсталлятор добавляет в конец каждого agent definition
стандартный блок (дословно, адаптируя только формат канала):

> После этого блока добавляется профиль модели — см. процедуру 5.

```
## Дисциплина исполнения
- Выполняй задачу САМ, своими инструментами. Не запускай других агентов и не жди
  «фоновых» процессов — у субагента их нет: никто ничего за тебя не сделает,
  уведомление не придёт.
- Запустил команду — дождись её результата в этом же вызове; длительные операции
  разбивай на шаги с проверяемым результатом каждого.
- Временные файлы — только в служебном каталоге проекта `var/tmp/` (git-ignored),
  не в корне проекта и не вне его. Убери за собой то, что не является результатом.
- Задача завершена, когда написан финальный отчёт (Handoff). Написал отчёт —
  остановись: не продолжай «улучшать», не жди подтверждений и новых указаний.
```

### 5. Блок «Профиль модели» (добавляется при рендере по семейству модели)

После резолва модели агента (процедура 1) инсталлятор определяет **семейство**
резолвнутой модели по таблице в `core/channels/model-profiles.md` и добавляет
в конец agent definition соответствующие профильные блоки — сразу после блока
«Дисциплина исполнения». Для Claude-моделей это общий блок + блок конкретной
модели (если определён); для GPT-моделей — блок GPT. Профиль — рендер-добавка
(при обновлении переприменяется по ONBOARD §9.5), тела ролей он не меняет.
Модельная специфика живёт только в `model-profiles.md` — не в телах ролей и
не в правилах. Если семейство модели не определяется (сторонние/локальные
модели), профиль не добавляется — инсталлятор фиксирует «no profile» в отчёте
установки.
