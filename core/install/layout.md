# Раскладка дистрибутива в целевой проект

Источник контента один: `core/` (+ `overlays/<stack>/`, если стек подтверждён на установке).
Этот файл ничего не добавляет к содержанию — он описывает только КУДА и в каком ФОРМАТЕ
инсталлятор раскладывает этот единственный источник.

Цель одна — **Claude Code**. Раскладок под другие среды дистрибутив не несёт: попытка
обслуживать несколько сред разом стоила больше, чем давала, и была снята (см. `docs/TODO.md`).

Резолв модели агента: `tier` роли (`core/agents/ROLES.md`) → `core/install/model-map.yaml` →
значение по tier. Усилие резолвится тем же ходом: `effort` роли → `claude.effort.<значение>`.
Общая процедура — в конце файла.

---

## Корень проекта

- `AGENTS.md` — корневой контракт. Единственный источник: роли, MCP-профиль, дисциплина
  вывода. Всё остальное на него ссылается.
- `rules/` — тела правил (`core/rules/*` + `overlays/<stack>/rules/*`, если стек подтверждён).
- `openspec/` — скаффолд воркспейса.
- `CLAUDE.md` — ровно одна строка: `See @AGENTS.md`.

  **⚠ Грабля:** без символа `@` Claude Code не распознаёт директиву импорта — файл не
  подтягивается, контракт молча не загружается, и агент работает без него, не сообщая об
  ошибке.

- **Правила лежат только в корневом `rules/`.** Каталог `.claude/rules/` не используется и
  не создаётся.

  **⚠ Грабля:** тела правил нельзя класть в `.claude/rules/` — Claude Code индексирует всё
  содержимое этого каталога как always-on контекст (подгружается в каждый промпт целиком,
  порядка десятков тысяч токенов на полный набор правил), что убивает ленивую по-требованию
  загрузку, на которой строится вся структура дистрибутива. Каталог `.claude/rules/` не
  должен существовать в раскладке вообще.

- `.mcp.json` — `{ "mcpServers": { … } }`, один блок на сервер из декларации MCP проекта.

  **⚠ Грабля:** у серверов, доступных по сети (не через локальный процесс), обязательно поле
  `"type": "http"`. Без него Claude Code по умолчанию считает сервер локальным процессом,
  ищет поле `command`, не находит и молча пропускает сервер при старте — никакой ошибки в
  интерфейсе не будет, сервер просто не появится в списке подключённых.

## Каталог `.claude/`

- `.claude/agents/<role>.md` — один файл на роль:
  - frontmatter: `name`, `description`, `model`, `effort`, `tools`, `allowParallel`;
  - `model` — резолвится из `model-map.yaml` по tier роли (см. общую процедуру резолва
    ниже); override-tier `fast` не определён, поэтому роли с `override: fast` получают свой
    базовый tier;
  - `effort` — резолвится из `claude.effort` по колонке `effort` роли; поле переопределяет
    усилие сессии на время работы субагента. Верхняя ступень в раскладку не пишется
    никогда — только ручная эскалация на конкретный запуск;
  - `tools` — псевдо-значения `ro`/`rw` из `ROLES.md` разворачиваются в реальные имена
    инструментов: `ro` → `["Read", "Grep", "Glob"]` + MCP-инструменты, объявленные для
    проекта на установке; `rw` → тот же набор плюс `["Write", "Edit", "Bash"]`.

  **⚠ Грабля:** псевдоимена вида `Shell`/`MCP` в allowlist инструментов Claude Code не
  распознаются — список обязан состоять из настоящих имён инструментов (`Bash`, а не
  `Shell`; конкретные `mcp__<server>__<tool>`, а не общее слово `MCP`).

- `.claude/skills/<skill>/` — копия из `core/skills/<skill>/` (+ оверлейные skills, если стек
  подтверждён). Исключение — скиллы с внешним рантаймом: `archify` (схемы в HTML/PNG, 2,3 МБ)
  ставится, только если в окружении цели есть Node ≥ 18 (`node --version`, ONBOARD §1); npm
  ставить не нужно. Нет Node — скилл не копируется, в отчёте (§11) одна строка: «archify не
  установлен — нет Node ≥ 18». Проектный скилл `archify` глобальную копию
  (`~/.claude/skills/archify`) перекрывает; две копии с одним именем — источник путаницы,
  глобальную стоит убрать. То же условие у оверлейного `1c-config-docs` (документация
  конфигурации по коду; схемы строит через `archify`); его npm-зависимость (`docx`) ставится
  не при установке, а при первом использовании — `npm ci` в `scripts/` скилла, каталог
  `node_modules/` закрыт его собственным `.gitignore`.
- `.claude/commands/*.md` — копия из `core/commands/*.md` (+ оверлейные
  `overlays/<stack>/commands/*`, если стек подтверждён).
- `.claude/hooks/` — только если ставится хук напоминания правил (ONBOARD §4.2, §5.1).

## Опционально: прокси сжатия вывода команд (rtk)

Если пользователь применяет `core/rules/tool-output-economy.md` глубже, чем явные
`rtk`-префиксы, доступен автоперехват через PreToolUse-hook (`rtk init -g` — ставит только
сам пользователь; инсталлятор дистрибутива хуки rtk НЕ создаёт и НЕ меняет).

**⚠ Грабля:** hook перехватывает только вызовы инструмента Bash — встроенные Read/Grep/Glob
через него не проходят и не переписываются; экономия на них достигается только явными
`rtk read`/`rtk grep`-вызовами по правилу. Второй нюанс: `rtk ls`/`tree` требуют coreutils
в PATH (в bash-сессии есть, в чистом PowerShell — нет; там пользоваться raw-командами).

**⚠ Грабля:** проектный `rtk init` (без `-g`) НЕ ставит hook — он пишет свои инструкции в
`CLAUDE.md`, а канон требует, чтобы `CLAUDE.md` содержал ровно `See @AGENTS.md`.
В airules-раскладке проектный `rtk init` не использовать: инструкции агенту уже несёт
правило `tool-output-economy`, а автоперехват — только глобальный `rtk init -g` (решение
пользователя). Проектные фильтры `.rtk/filters.toml` требуют разового одобрения
пользователем на машине (`rtk trust`).

## Общие процедуры

### 1. Резолв модели и усилия

1. Взять `tier` и `effort` роли из `core/agents/ROLES.md`.
2. Найти значение по адресу `claude.<tier>` в `core/install/model-map.yaml`.
3. Если роль несёт `override: fast` и tier `fast` определён — использовать его вместо
   базового; если не определён — оставить базовый tier роли (см. семантику override в
   `ROLES.md`).
4. Найти усилие по адресу `claude.effort.<effort роли>`. Если роль не несёт `effort`
   (оверлейное определение вне реестра) — оставить дефолт сессии.
5. Записать модель и усилие в agent definition как поля frontmatter.
6. **Условный тир** (роль помечена `*` в реестре — сейчас `analytic`): рендерится **парой**
   определений из одного тела роли — `<role>` на базовых tier/effort и `<role>-deep` на
   повышенных из секции «Conditional tiers» реестра (`name`/имя файла получают суффикс
   `-deep`). Обе строки попадают в `{{AGENTS_TABLE}}`; выбор на запуске делает оркестратор.

### 2. Маппинг tools

| псевдо-значение (`ROLES.md`) | разворачивается в |
| --- | --- |
| `ro` | `["Read", "Grep", "Glob"]` + MCP-инструменты серверов с `access: ro` + два читающих инструмента сервера памяти, если он подключён (правило ниже) |
| `rw` | `ro` + `["Write", "Edit", "Bash"]` |

**ro-роли и мутирующие серверы.** В allowlist ro-роли попадают только серверы,
помеченные в MCP-инвентаре `access: ro` (классификация — ONBOARD §1.1: сервер с
хотя бы одним мутирующим инструментом = `rw`, при сомнении — `rw`). `rw`-сервер
в ro-развёртку не попадает целиком; отдельные его читающие инструменты можно
включить только при достоверно известном инвентаре (правило ниже). `rw`-роли
получают серверы обоих классов. Текстовый запрет мутаций в теле ro-роли
остаётся обязательной страховкой — на случай ошибочной классификации.

**Allowlist MCP по префиксу сервера.** Инвентарь инструментов сервера оффлайн недоступен
(перечень `mcp__<server>__<tool>` можно узнать только у живого сервера), поэтому в allowlist
агентов ДОПУСТИМ и является дефолтом префикс сервера целиком: `mcp__<server>` (= все
инструменты этого сервера). Перечислять конкретные `mcp__<server>__<tool>` — только когда
инвентарь достоверно известен (живое подключение или инвентарь, поставляемый с профилем
проекта). Выдуманные имена инструментов запрещены. Имя сервера в префиксе — каноническое
(см. нормализацию имён в ONBOARD §7).

**Сервер памяти — исключение из обоих правил выше.** В allowlist ролей он входит не
префиксом, а ровно двумя инструментами поимённо: **поиск** и **чтение записи по
идентификатору**. Оба читающие, поэтому их получают **все роли, включая `ro`**, хотя сам
сервер классифицирован `rw`. Ни один пишущий, удаляющий или служебный инструмент сервера
памяти в роли не попадает — ни в `ro`, ни в `rw`: в память пишет оркестратор (ему сервер
доступен целиком через `.mcp.json`), субагент отдаёт то, что стоит запомнить, в отчёте.

Имена двух инструментов берутся из живого `tools/list` сервера — рукопожатие с ним
установка и так обязана сделать (ONBOARD §4.3, шаг 2). Если у сервера несколько видов
поиска, берётся один — тот, что сочетает поиск по словам и по смыслу. Список инструментов
получить не удалось — сервер памяти в роли не пишется вовсе, в отчёте установки (§11)
одна строка об этом; подставлять префикс «на всякий случай» нельзя.

Почему не префикс. Схемы всех инструментов сервера, названного в `tools:` префиксом,
грузятся в контекст субагента на **каждом** его запуске и остаются там на каждом
обращении к модели. У сервера памяти инструментов десятки; замер на типичном сервере:
префикс — около 16 тыс. токенов на запуск роли, два инструмента поимённо — около 1,6 тыс.
Второе следствие префикса — массовое удаление, импорт и пересборка индекса памяти в руках
каждого субагента.

### 3. Инстанцирование инструментальных упоминаний

Тела **агентов** ссылаются на инструменты обобщённо (прозаически, например «инструменты
поиска по коду проекта»). При раскладке под конкретный проект инсталлятор обязан заменить
такие прозаические упоминания на конкретные имена MCP-инструментов, обнаруженные на шаге
детекта проекта (см. процедуру ONBOARD), и подтвердить подстановку на шаге верификации
ONBOARD — прозаическая формулировка в разложенном агенте является признаком незавершённой
установки. При применённом MCP-профиле оверлея (ONBOARD §1.1) таблица подстановки и
allowlist ролей берутся из профиля. **Правила (`rules/`) не инстанцируются**: они намеренно категориальны
(«категории инструментов профиля проекта»), копируются дословно и обновляются
sha-сверкой — подстановка имён сломала бы update-цикл; конкретику правилам даёт
MCP-профиль корневого контракта.

### 4. Блок «Дисциплина исполнения» (добавляется при рендере каждому агенту)

Инсталлятор добавляет в конец каждого agent definition стандартный блок дословно:

> После этого блока добавляется профиль модели — см. процедуру 5.

```
## Дисциплина исполнения
- Выполняй задачу САМ, своими инструментами. Не запускай других агентов и не жди
  «фоновых» процессов — у субагента их нет: никто ничего за тебя не сделает,
  уведомление не придёт.
- Запустил команду — дождись её результата в этом же вызове; длительные операции
  разбивай на шаги с проверяемым результатом каждого.
- Временные файлы — только в служебном каталоге проекта `var/tmp/` (git-ignored),
  не в корне проекта и не вне его. Убери за собой то, что не является результатом.
- Задача завершена, когда написан финальный отчёт (Handoff). Написал отчёт —
  остановись: не продолжай «улучшать», не жди подтверждений и новых указаний.
```

Если к проекту подключён сервер памяти, в тот же блок добавляется ещё один пункт —
дословно, с подставленными именами двух инструментов (процедура 2). Сервера памяти нет —
пункт не добавляется:

```
- Память проекта: тебе доступны только поиск (`<инструмент поиска>`) и чтение записи
  (`<инструмент чтения>`). Найденное — прежнее наблюдение, а не доказательство: сверь с
  источником истины. Если сервер общий для нескольких проектов — ограничивай поиск
  своим проектом, иначе придут чужие записи. В память не пишешь: то, что стоит
  запомнить, вынеси в отчёт отдельным пунктом «В память» — запишет оркестратор.
```

### 5. Блок «Профиль модели» (добавляется при рендере по семейству модели)

После резолва модели агента (процедура 1) инсталлятор определяет **семейство**
резолвнутой модели по таблице в `core/install/model-profiles.md` и добавляет
в конец agent definition соответствующие профильные блоки — сразу после блока
«Дисциплина исполнения»: общий блок Claude плюс блок конкретной модели, если
он определён. Профиль — рендер-добавка (при обновлении переприменяется по
ONBOARD §9.5), тела ролей он не меняет. Модельная специфика живёт только в
`model-profiles.md` — не в телах ролей и не в правилах. Если семейство не
определяется, профиль не добавляется — инсталлятор фиксирует «no profile» в
отчёте установки.
