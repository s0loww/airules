# ONBOARD — установка дистрибутива airules в целевой проект

> **Кому.** Этот документ исполняет **агент** — Claude Code. Это **инструкция,
> а не скилл**: специфичного рантайма не требует, выполняется обычными
> действиями «прочитать файл / записать файл / выполнить команду оболочки».
>
> **Что делает.** Разворачивает в ЦЕЛЕВОМ проекте переносимый слой airules:
> корневой контракт агента, библиотеку правил с ленивой загрузкой, паспорт
> проекта (OpenSpec), MCP-конфиг и раскладку `.claude/`. Доменную специфику
> исходных проектов НЕ переносит —
> переносит **схему** дистрибутива, а факты целевого проекта собирает заново.
>
> **Standalone.** airules — самодостаточный дистрибутив. Никакого внешнего
> движка, платформенного роутинга или рантайма он не требует и не разворачивает:
> роутинг «триггер → правило → роль» встроен в `AGENTS.md`, синхронизация — по
> манифесту `.airules-manifest.json` (см. `docs/SYNC.md`).

Здесь и далее «дистрибутив» = каталог airules, который тебе дали как источник;
«цель» = репозиторий, в котором ты сейчас работаешь.

---

## 0. Безопасность (соблюдать всегда)

- **Ничего не удалять** без отдельного явного разрешения пользователя.
- Перед перезаписью существующих `AGENTS.md`, `CLAUDE.md`, `.mcp.json`,
  `.claude/*`, `rules/*`, `openspec/*` — снять **бэкап** в
  `.rules-backups/<timestamp>/` (или в `{{BACKUP_DIR}}`, если задан другой) с
  сохранением относительных путей.
- **Не копировать секреты** (токены, webhook, пароли, ключи, персональные
  абсолютные пути) из исходного окружения в переносимые файлы. Секреты — только
  в git-ignored файл окружения.
- Если рабочее дерево цели **dirty** — чужие изменения не откатывать и не
  трогать; ставить рядом.
- Все плейсхолдеры `{{…}}` заменить фактами цели; если факт нельзя безопасно
  установить — оставить явный маркер `НЕ НАСТРОЕНО: <что выяснить>`, а не
  выдумывать.
- Идемпотентность: повторный запуск не ломает установленное (сверяй, потом пиши;
  режим update — §9).
- **Установка ОБЯЗАНА завершиться записью `.airules-manifest.json`** (§8). Без
  манифеста установка считается **незавершённой** — последующее безопасное
  обновление (§9) без него невозможно.

## 1. Разведка окружения цели

Собери факты, выводимые **без вопросов**.

1. **Стек/тип проекта** (`STACK`). Признаки: `package.json` → node/web;
   `pyproject.toml`/`requirements.txt` → python; `go.mod` → go; XML-метаданные
   конфигурации и `*.bsl` → `1c`; и т. п. Зафиксируй значение.
2. **Корень исходников** (`PRIMARY_CODE_DIR`): где лежит код/метаданные (`src/`,
   `app/`, `lib/`…).
3. **Существующая обвязка:** есть ли `AGENTS.md`, `CLAUDE.md`, `.claude/`,
   `.mcp.json`, `openspec/`, `rules/`, `.airules-manifest.json` —
   чтобы не затереть, а дополнить (с бэкапом). Наличие манифеста → переходи в
   режим update (§9).
4. **Репозиторий:** корень, основная ветка, git-статус (dirty?).

### 1.1 Детект MCP-серверов

Не спрашивай endpoints вслепую — **сначала задетекть**. Просканируй то, что
существует; **JSON-конфиги читать BOM-толерантно** (кодировка `utf-8-sig`):

| Источник | Путь | Что парсить |
|---|---|---|
| Claude Code (глобальный) | `~/.claude.json` | `projects[<путь-цели>].mcpServers` |
| Claude Code (проект) | `<цель>/.mcp.json` | `mcpServers` (top-level) |
| Claude Desktop | `%APPDATA%/Claude/claude_desktop_config.json` (win) / `~/Library/Application Support/Claude/…` (mac) | `mcpServers` |
| Локальные сервисы | `docker ps`, слушающие порты | имя/порт/health |

Приведи каждый сервер к записи `{ name, transport (http|stdio), url|command,
env, description, source, access (ro|rw) }`. **`access`** — мутирует ли сервер
состояние: `rw`, если сервер экспонирует хотя бы один мутирующий инструмент
(запись/изменение/удаление данных или файлов, деплой, выполнение команд);
`ro` — только чтение/поиск/навигация. Классификация best-effort из
описания/доков сервера; **при сомнении — `rw`**. **Креды из `url` в инвентаре
и в отчёте маскируй** (`***`). Дубли по имени схлопни, отметив источник. Это
вход для §2.4 (подтверждение) и §7 (генерация конфигов); `access` управляет
allowlist ro-ролей (layout §2).

### 1.2 Детект моделей (best-effort)

Попробуй по порядку то, что доступно; что не вышло — уйдёт в вопрос §2.

- **Своя модель агента:** агент обычно знает свою текущую модель — кандидат как
  минимум на свой tier.
- **Глобальный конфиг:** `~/.claude/settings.json` может нести выбранную модель.

Сопоставь найденное с тирами high/medium/low. Дефолт — маппинг из
`core/install/model-map.yaml`; спрашивать пользователя нужно только если
задетекченное ему противоречит. «Доступно» ≠ «оплачено/разрешено».

## 2. Интервью (спросить только невыводимое)

Спрашивай **коротко и пакетом**. Не спрашивай выведенное в §1.

1. **Модели по тирам** — дефолт берётся из `core/install/model-map.yaml` и
   подтверждения не требует. Спрашивать только если пользователь хочет иную
   раскладку тиров или если задетекченное (§1.2) противоречит карте.
2. **Project ID** (короткий, `[a-z0-9-]`) и **имя проекта** (`PROJECT_NAME`).
3. **Источник истины** (`SOURCE_OF_TRUTH`): какой каталог/набор файлов финально
   авторитетен (напр. `src/`).
4. **Подтверждение MCP-инвентаря** (§1.1): какие включить, **порядок приоритета**
   (`MCP_ORDER`), какие **исключить** (`DISABLED_MCP` — устаревшие/отключённые
   индексы), и подтверждение классификации **`access: ro|rw`** каждого сервера
   (управляет тем, что попадёт в allowlist ролей только-чтение).
5. **Контур памяти** — три варианта, спросить явно:
   - **подключить к существующему серверу памяти** — запросить URL эндпоинта
     (`http://<хост>:<порт>/mcp`) и проверить его до записи в конфиг
     (см. §4.3, шаг проверки). Дефолт, если сервер в организации уже есть;
   - **развернуть свой** — по рецепту §4.3; выбирать, когда общий слой памяти
     нужен нескольким машинам или инструментам;
   - **не использовать** — остаётся только файловая память Claude Code. Полностью
     рабочий вариант: ничего в дистрибутиве от сервера памяти не зависит.
6. **Опциональное** (есть дефолты или `НЕ НАСТРОЕНО`): префикс имён объектов
   (`PREFIX`) — для стеков, где он нужен; доменный оверлей (§5); языковая
   политика ответов и кода (`LANGUAGE_POLICY`, по умолчанию — как в команде);
   backup-каталог, если не `.rules-backups/`.

## 4. Ядро (ставится всегда)

Слой, работающий на любом агенте без зависимостей.

### 4.1 Состав ядра

Список маркированный намеренно: нумерованным он давал вторую систему
координат — ссылка «§4.2» означала бы и подраздел, и пункт списка.

- **`AGENTS.md`** (корень) — из `core/templates/AGENTS.md`. Заполнить факты
   §3; собрать **Rule Index** из фактически установленных правил (§4.2);
   встроить **мини-таблицу роутинга** (шаблон её уже содержит — заполнить
   доменные строки `{{DOMAIN_*}}` из оверлея либо оставить generic); заполнить
   таблицу агентов (`{{AGENTS_TABLE}}`, §6) и MCP-строки (`{{MCP_ORDER}}` /
   `{{DISABLED_MCP}}`, §7).
- **`rules/`** (корень) ← копия **всех** `core/rules/*` (актуальный состав —
   листингом каталога дистрибутива, не по памяти); при подтверждённом стеке —
   плюс `overlays/<stack>/rules/*` (§5).
- **`openspec/`** (корень) ← `project-template/openspec/*` в режиме
   **skip-if-exists** (существующие specs/changes не перезаписывать). Заполнить
   `openspec/project.md` фактами §3; неизвестное пометить `НЕ НАСТРОЕНО`.
- **`env.example`** (корень) ← `project-template/env.example` — только если
   стеку нужны локальные креды (напр. COM-скрипты). Реальный `.env` не
   создавать; добавить `.env` в `.gitignore`.
- **Память проекта** — memory-файл по соглашению целевого рантайма (заметки
   стабильных решений, без секретов/PII). Если у рантайма своего соглашения
   нет — `memory.md` в корне. Ставится **всегда**, независимо от ответа про
   сервер памяти (§2.5): см. границу слоёв в §4.3.
- **Служебный каталог** — создать `var/tmp/` (рабочая папка субагентов для
   временных файлов; блок «Дисциплина исполнения» агентов указывает на неё) и
   добавить `var/tmp/` в `.gitignore` цели.
- **`.gitattributes`** (корень) ← `project-template/gitattributes.example`,
   если цель — git-репозиторий. Существующий файл не перезаписывать, а
   дописать недостающие строки. Из шаблона убрать пути каталогов, которые в
   этой установке не создавались; проектные каталоги в него НЕ добавлять.

   > **⚠ Грабля (стоила полного расхождения манифеста на боевом проекте).**
   > Манифест хранит sha256 от байтов файла как есть, без нормализации
   > содержимого (`docs/SYNC.md`). При `core.autocrlf=true` — а это дефолт git
   > для Windows — checkout подменяет переводы строк, байты меняются, sha
   > перестаёт сходиться. Следующее обновление (§9) увидит КАЖДЫЙ управляемый
   > файл как «изменённый пользователем» и вывалит сотни вопросов, вместо того
   > чтобы молча заменить неизменённое. Симптом коварен тем, что проявляется
   > не сразу после установки, а на первом свежем клоне цели.

### 4.2 Rule Index

Собери индекс **только из реально установленных** файлов `rules/`: одна строка
на правило — имя, краткое «когда читать» (бери из frontmatter `description`
файла), путь `rules/<имя>.md`. Состав определяется листингом установленного
каталога, а не фиксированным списком в этой инструкции.

Оверлейные правила (§5) добавляются строками в тот же индекс. Директива в
шаблоне — «правила НЕ предзагружать; читать через Read по мере соответствия
задаче» — сохраняется.

**Напоминание после сжатия (опционально).** Тело правила,
прочитанное через Read, живёт в истории и первым уходит при сжатии контекста,
а в summary остаётся строка «правило прочитано». Модель видит её, считает
вопрос закрытым и не перечитывает — правило формально загружено, фактически
его нет. Заплата: `core/hooks/rule-inject.py` → `.claude/hooks/`, и в
`.claude/settings.json` (существующий **не перезаписывать**, дописать событие):

```json
{
  "hooks": {
    "SessionStart": [
      {
        "matcher": "compact",
        "hooks": [
          {
            "type": "command",
            "command": "python",
            "args": ["${CLAUDE_PROJECT_DIR}/.claude/hooks/rule-inject.py", "--session-start"]
          }
        ]
      }
    ]
  }
}
```

Карта правил для этого режима не нужна — он ничего не знает о конкретных
правилах и говорит лишь, что тела выгружены. Проверка: скормить скрипту
`{"source":"compact"}` на stdin с ключом `--session-start` — должен напечатать
абзац; с `{"source":"startup"}` — промолчать. Нет Python — пропустить и
написать в отчёт установки. Второй режим того же скрипта (напоминание по пути
файла) ставится вместе с оверлеем, см. §5.1.

<a id="hook-liveness"></a>
**Регистрация — не запуск.** Проверка выше показывает только, что скрипт
корректно отвечает на вызов. Она ничего не говорит о том, зовёт ли его среда.
Замерено 2026-08-14 на `claude-desktop 2.1.229` и `claude` CLI 2.1.224
(Windows): проектный `.claude/settings.json` исполняется и в десктопе, и в CLI — но
**не сразу**. В десктоп-клиенте, запущенном в проекте, где каталога `.claude`
ещё не было, три вызова подряд не дали ни одного запуска; после перезапуска
клиента запись той же формы сработала. В CLI, где каждый прогон — новый
процесс, срабатывает всегда.

Отсюда практическое: **поставил хук в проект, где `.claude` не было —
перезапусти клиент**, и только потом проверяй. Точный критерий подхвата не
установлен (правдоподобно, что каталог должен существовать на момент старта
клиента), поэтому полагаться надо не на объяснение, а на проверку ниже.

**Регистрации складываются, а не вытесняют друг друга.** Проверено на одном
вызове: сработали одновременно две записи с matcher `Bash` из проектного файла
и запись с тем же matcher из `~/.claude/settings.json`. Так что занятый кем-то
matcher — не причина не ставить свой хук; вытеснения нет ни между источниками,
ни внутри одного файла.

Осторожность нужна другого рода: если чужой хук на том же событии **меняет**
вызов (обёртки, переписывающие команду), то конфликт будет не за регистрацию, а
за смысл — два хука правят одно и то же. Это смотреть глазами, автоматически не
ловится.

Убедиться можно только зондом, который пишет **собственный** лог: молчание в
контексте само по себе неразличимо для трёх разных причин.

| Строка в контексте | Строка в логе зонда | Что произошло |
|---|---|---|
| есть | есть | хук запущен, вывод доставлен — рабочий случай |
| нет | есть | хук запущен, вывод до модели не доехал — не та точка регистрации или не то событие |
| нет | нет | хук не запускался — конфиг не подхвачен (подождать, затем перезапустить клиент) |

Зонд: скрипт, который дописывает в лог отметку времени и `source` из stdin и
выходит с нулём. Регистрировать на то же событие, что и боевой хук, но **без**
`matcher` — так он ловит все source и показывает, какие вообще наступают.
Отметка времени обязательна: без неё нельзя отличить свежий запуск от старой
строки. Если проектная точка молчит — сначала перезапустить клиент и повторить,
затем проверить, не занят ли matcher; и только если и это не помогло —
перенести регистрацию в пользовательский конфиг и написать об этом в отчёте
установки (§8).

**Группировка по жанру.** У каждого правила во frontmatter есть поле `kind` —
`invariant` (что всегда верно про код такого-то вида; привязано к файлу),
`case` (симптом → фикс), `recipe` (задача → процедура), `process` (как вести
работу), `router` (навигация к соседним правилам). Индекс собирать
**сгруппированным по `kind`**, инварианты первой группой, и жанр указывать в
строке правила: он говорит, **когда** правило нужно, тогда как `description`
говорит, **о чём** оно. Порядок внутри группы — алфавитный. Если у
установленного правила поля `kind` нет — это дефект дистрибутива: поставь
строку в индекс без группы и сообщи об этом в отчёте установки (§8).

### 4.3 Сервер памяти (опционально, по ответу §2.5)

Сервер памяти — общий слой для нескольких машин и инструментов: одна база,
клиенты ходят через MCP. Дистрибутив от него **не зависит**: без него работает
файловая память Claude Code, и ни одно правило не перестаёт действовать.

#### Граница слоёв — задать до подключения

| Слой | Где живёт | Почему так |
|---|---|---|
| **Конституция** — правила, договорённости, топология, пути, что нельзя трогать | markdown под git (`AGENTS.md`, `rules/`, memory-файл) | diff, ревью, откат, бэкап. База — блоб: его не поревьюить и не смерджить |
| **Операционный поток** — что делали в сессии, инциденты, находки, TODO | сервер памяти | растёт быстро, ищется по смыслу, нужен с нескольких машин |

Смешать их — получить два источника истины с расходящимися фактами, причём оба
лезут в контекст в один и тот же слот на старте сессии. Границу зафиксировать в
`AGENTS.md` цели одной строкой, иначе она размывается молча.

#### Вариант А — подключение к существующему серверу

1. Запросить URL эндпоинта у пользователя. **Не угадывать и не подставлять
   адреса из примеров.**
2. **Проверить до записи в конфиг** — рукопожатием MCP, а не «пингом»:
   POST на эндпоинт с `Accept: application/json, text/event-stream` и телом
   `initialize`. Ожидание: `200` и `serverInfo` в ответе. Голый GET на
   streamable-http эндпоинт отдаёт `406` — это норма, а не поломка.
3. Записать в проектный `.mcp.json` (по
   их конвенции, §6). **Проектный, не глобальный**: сервер памяти приносит
   несколько десятков инструментов, и в глобальном конфиге они попадут в
   каждую сессию любого проекта.
4. Если адрес машинный — `.mcp.json` в `.gitignore`, а под git положить
   `.mcp.json.example` с плейсхолдером вместо хоста.

#### Вариант Б — развернуть свой

Разворачивать контейнером, а не на хост: снос без следа, версия фиксирована.
Что решить осознанно, помимо запуска:

- **Пин версии.** Ставить с запиненного тега или коммита. Иначе смена схемы
  БД приезжает в живую базу молча, при очередном пересборе образа.
- **Один процесс-владелец базы.** Все клиенты — к одному серверу по сети.
  Класть файл БД на сетевую шару и поднимать по процессу на машину нельзя:
  SQLite поверх SMB/NFS — это порча базы.
- **Не биндить наружу.** Слушать loopback и отдавать через приватную сеть;
  своей авторизации у таких серверов обычно нет, периметр — ACL сети.
- **Том для базы.** Без volume база живёт ровно до пересоздания контейнера.
- **Эмбеддинги.** Локальная модель или внешний API. Внешний дешевле по
  железу, но тогда **запись памяти зависит от живости провайдера и канала связи до
  него** — для памяти это плохой вид связанности, решать осознанно.
- **Автозахват выключить на старте.** Хуки, пишущие память сами, включать
  после того, как станет ясно, что стоит запоминать.
- **Бэкап базы по расписанию.** Она станет единственным местом хранения
  операционной истории.

После разворачивания — шаги 2–4 варианта А.

#### Проверка

`memory`-инструменты появляются в **следующей** сессии, а не в текущей. В
отчёте установки (§11) указать: подключён сервер памяти или нет, каким
вариантом, и что граница слоёв записана в `AGENTS.md`.

## 5. Доменный оверлей (опционально, по подтверждению)

Только при подтверждённом стеке (§2.6) и согласии пользователя: доставь
`overlays/<stack>/rules/*` в `rules/` и добавь строки в Rule Index; доменные
строки мини-таблицы роутинга (`{{DOMAIN_*}}`) заполни из оверлея. **Доменную
специфику конкретного исходного проекта не тащить** — она остаётся в памяти
цели, помеченная как проектное решение, а не универсальный стандарт (входной
фильтр — `docs/LAYERS.md`).

Уточнения состава оверлея:

- **Агенты**: `overlays/<stack>/agents/*` — полные определения, при установке
  **замещают** generic-роли целиком (не смешивать два набора). Имя файла agent
  definition — по `name` из frontmatter агента.
- **Роутинг**: доменные строки мини-таблицы бери из README оверлея (секция
  «Роутинг»); если её нет — по `description` правил оверлея. Строку отладки
  не замещать: оверлейная адаптация дописывается рядом с `debugging-loop`
  (примечание таблицы в шаблоне).
- **Файлы-шаблоны оверлея** (имена вида `<имя>.example` в корне оверлея):
  копировать в корень цели с точкой (`dev.env.example` → `.dev.env.example`)
  и создать рабочий файл (`.dev.env`), заполнив поля, известные из §1–§2
  (префикс, версия платформы), — остальные спросить пакетом §2 или пометить
  `НЕ НАСТРОЕНО`.
- **Библиотеки** `overlays/<stack>/tools/*` (если есть): копировать в
  `tools/<имя-библиотеки>/` — путь **нормативный, не рекомендуемый**. Правила
  стека ссылаются на эти библиотеки буквально (`tools/com-tools/` и
  подобные); установка в другое место оставляет правило со ссылкой в никуда,
  причём молча. Путь упомянуть в `AGENTS.md`.
- **Команды** `overlays/<stack>/commands/*` (если есть): доставлять тем же
  путём, что и core-команды (`.claude/commands/`).
- **Память**: контур памяти общий для всех стеков и описан в §4.3 — здесь
  ничего оверлейного нет.

### 5.1 Хук напоминания правил (опционально)

Ставится **только** если у оверлея есть `hooks/rules-map.json` и в целевой
системе есть `python` в `PATH`. Нет карты или нет Python — пропустить и
написать об этом в отчёте установки; всё остальное работает без хука.

Зачем: тело правила, прочитанное через Read, живёт в истории и первым уходит
при сжатии контекста, а в summary остаётся строка «правило прочитано» — модель
считает вопрос закрытым и не перечитывает. Хук не история, а реакция на
действие: он срабатывает заново на каждой правке подходящего файла. Инжектится
**не тело правила**, а путь к нему и одна строка инварианта.

1. Скопировать `core/hooks/rule-inject.py` → `.claude/hooks/rule-inject.py`
   (если он уже поставлен по §4.2 — это тот же файл, копировать повторно не
   нужно).
2. Скопировать `overlays/<stack>/hooks/rules-map.json` → рядом со скриптом,
   в `.claude/hooks/rules-map.json`. Скрипт ищет карту только там.
3. Зарегистрировать в `.claude/settings.json`. **Существующий файл не
   перезаписывать** — дописать событие в имеющийся объект `hooks`, сохранив
   всё остальное:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "python",
            "args": ["${CLAUDE_PROJECT_DIR}/.claude/hooks/rule-inject.py"]
          }
        ]
      }
    ]
  }
}
```

4. Сверить карту с тем, что реально установлено:

```
python .claude/hooks/rule-inject.py --check-map
```

Ожидание: `карта: N запись(ей), все правила на месте`. Проверка ловит четыре
способа получить мёртвое напоминание: ссылку на неустановленное правило
(частая при частичной установке оверлея), правило не с `kind: invariant`,
пустой инвариант (впрыснётся голый путь) и запись без масок. Каждый дефект —
это строка, которая печатается в контекст и ни к чему не ведёт; при отказе
либо доставить недостающее правило, либо убрать запись из карты, и написать об
этом в отчёте установки (§8).

5. Проверить, что впрыскивается — скрипт умеет сухой прогон:

```
python .claude/hooks/rule-inject.py --dry-run <путь из карты>
```

Ожидание: для пути, попадающего под маску, печатаются строки правил; для
постороннего файла — «no rule matches this path». Если печатается пусто на
всём — карта не найдена рядом со скриптом. Если пусто на пути, который под
маску попадает, — сверить, что вывод не рвётся на кодировке: скрипт
переключает stdout в UTF-8 сам, но это первое, что стоит проверить, потому что
такой отказ выглядит как «маска не сработала».

6. Убедиться, что точка регистрации живая — сухой прогон этого не показывает,
   см. «Регистрация — не запуск» в §4.2. Для `PreToolUse` зонд ставится на
   `matcher: "Bash"` и проверяется одним вызовом Bash: так триггер не зависит
   от того, есть ли под рукой файл, попадающий в карту. Занятость matcher'а
   помехой не является — регистрации складываются. Зонд после проверки снять.

Границы, которые важно не нарушить при доработке карты:

- **В карту попадают только правила с `kind: invariant`** — те, что нужны в
  момент написания строки и опознаются по пути файла. Рецепты, кейсы и
  процессные правила остаются на ленивом индексе; дублировать их хуком —
  завести второй механизм подгрузки, который начнёт спорить с первым.
- **Маски узкие.** Хук, который срабатывает там, где правило не применяется,
  учит игнорировать инжект — как аларм, на который перестали смотреть.
- **Скиллы не трогать**: у них свой триггер по `description`.

## 6. Раскладка

**Раскладку не дублируй** — норматив «куда что кладётся, резолв модели,
грабли, tools-маппинг» описан в `core/install/layout.md`. Здесь — только
короткая карта и точки резолва.

| Куда | Что |
|---|---|
| корень | `AGENTS.md`, `CLAUDE.md` (ровно `See @AGENTS.md`), `rules/`, `openspec/`, `.mcp.json` |
| `.claude/` | `agents/*.md`, `commands/*`, `skills/*`, при необходимости `hooks/` |

Полные правила и все грабли — в `core/install/layout.md`.

**Резолв модели агента:** tier роли из `core/agents/ROLES.md` →
`core/install/model-map.yaml` (`claude.<tier>`). Override `fast` применяется по
семантике `ROLES.md` (роль с `override: fast` берёт `claude.fast`, если он
определён; иначе — свой базовый tier). Из этого резолва заполняется таблица
`{{AGENTS_TABLE}}` в `AGENTS.md` и поле модели в agent definition.

**Резолв усилия агента:** колонка `effort` роли → `claude.effort.<значение>`.
Верхняя ступень (`max`) в раскладку не пишется никогда: только ручная эскалация
на конкретный запуск. Источник ролей — `core/agents/ROLES.md`
(+ `overlays/<stack>/agents/*` при стеке); tools-псевдозначения `ro`/`rw`
разворачиваются по таблице в `core/install/layout.md`.

## 7. MCP-конфиги

Из подтверждённого инвентаря (§2.4) сгенерируй `.mcp.json`:
`{ "mcpServers": { … } }`. Remote-серверы **обязательно** с `"type": "http"` —
без него Claude Code молча пропускает сервер.

**Нормализация имён серверов.** Имя сервера в `.mcp.json` и в
tools-allowlist агентов (`mcp__<server>__*`) должно совпадать **буквально**.
Один и тот же сервер в разных источниках детекта может называться по-разному
(дефисы vs подчёркивания) — выбери одно каноническое имя, используй его во всех
конфигах и allowlist'ах установки и зафиксируй выбор в отчёте.

Порядок приоритета и исключения продублируй текстом в `AGENTS.md` (`{{MCP_ORDER}}`
/ `{{DISABLED_MCP}}`) — это единственный носитель роутинга. **Креды в конфиги не писать** (§0): секреты — в git-ignored окружении, в
url маскируются.

Сервер памяти (§4.3), если он подключается, — обычная запись того же инвентаря,
с двумя оговорками: она **проектная, а не глобальная** (десятки инструментов в
каждой сессии любого проекта того не стоят), и при машинном адресе рабочий файл
уходит в `.gitignore`, а под git остаётся `*.example` с плейсхолдером хоста.

## 8. Манифест установки

Установка завершается записью `.airules-manifest.json` в корень цели (формат —
`docs/SYNC.md`):

```json
{
  "version": "<из VERSION дистрибутива>",
  "installed_at": "<ISO-8601 timestamp>",
  "files": { "<relative-path>": "<sha256>" },
  "placeholders": { "<PLACEHOLDER>": "<заполненное значение>" }
}
```

- `version` — содержимое файла `VERSION` дистрибутива.
- `files` — каждый установленный/сгенерированный файл (относительный путь от
  корня цели → sha256 его содержимого). Именно по этим суммам режим update (§9)
  отличает пользовательскую правку от неизменённого файла.
- `placeholders` — фактически подставленные значения (§3); секреты сюда **не**
  писать.

Без валидного манифеста установка не считается завершённой (§0).

## 9. Обновление (update)

Если в цели **уже есть** `.airules-manifest.json` — запуск ONBOARD переходит в
режим update:

1. Для каждого файла из `manifest.files` сверь sha256 текущего файла цели с
   записанной суммой:
   - **не изменён пользователем** (суммы совпадают) → заменить новой версией из
     дистрибутива;
   - **изменён пользователем** (суммы расходятся) → спросить: оставить как есть
     или перезаписать. При перезаписи — предварительный бэкап в
     `.rules-backups/<timestamp>/`.
2. **Новый файл в дистрибутиве** (нет в манифесте) → добавить. Новое
   **правило** дополнительно вносится в Rule Index: пересобрать индекс
   листингом по §4.2 — независимо от того, менялся ли шаблон `AGENTS.md`
   (индекс — часть генерируемого файла, но его состав определяется
   фактическим содержимым `rules/`, а не шаблоном).
3. **Исчезнувший из дистрибутива** (есть в манифесте, нет в новой версии) →
   предложить удалить у пользователя (не удалять молча — §0).
4. **Генерируемые файлы** (`AGENTS.md`, `openspec/project.md` — параметризованы
   фактами проекта): их «источник изменился» определяется НЕ по манифесту, а по
   изменению шаблона-источника в дистрибутиве (diff/история шаблона между
   версиями). Изменился шаблон → обновлять только слиянием, сохраняя
   заполненные факты; не изменился → не трогать.
5. **Рендер-добавки раскладки**: agent definitions рендерятся из тел ролей;
   если между версиями изменились не тела, а правила рендера
   (`core/install/layout.md` — например, стандартный блок в конце agent
   definition) — переприменить рендер, тела ролей не трогая.
6. **Тела ролей и реестр**: если между версиями изменились сами тела ролей
   (`core/agents/roles/*`, оверлейные агенты) или их tier/effort/tools в
   реестре — **перерендерить** затронутые agent definitions по процедуре
   установки (§5–§6: тело + блок дисциплины + профиль модели). Локальные
   правки установленного определения обнаруживаются по манифесту и решаются
   развилкой шага 1 (спросить, бэкап перед перезаписью).
7. В конце **перепиши манифест** новой версией (новый `version`, `installed_at`,
   пересчитанные `files`, актуальные `placeholders`).

Если манифеста **нет**, но обвязка airules в цели присутствует — обновление
невозможно; допустима только **переустановка** с полным бэкапом и явным
подтверждением пользователя.

## 10. Верификация

- `rg "\{\{"` по установленным файлам → **ноль** незаполненных плейсхолдеров
  (кроме явных `НЕ НАСТРОЕНО`). Область проверки — файлы, которые
  параметризуются установкой (§3): `AGENTS.md`, `openspec/project.md`, конфиги,
  правила. **Не сканировать** два каталога, где `{{…}}` — не install-плейсхолдеры:
  скиллы (`.claude/skills/**`, `skills/**`) с собственной шаблонной нотацией и
  библиотеки (`tools/**`), где плейсхолдеры — рантайм-параметры, подставляемые
  из env-файла на запуске. Заполнять последние на установке **нельзя**: среди
  них креды, а §0 запрещает писать их в отслеживаемые файлы.
- Каждый файл, упомянутый в Rule Index и ссылках `AGENTS.md`, **существует**.
- В конфигах (`.mcp.json`, окружение) **нет секретов**.
- Чужие файлы не тронуты; бэкап снят при каждой перезаписи.
- **Манифест** `.airules-manifest.json` записан и валиден (JSON парсится,
  `files` непусты, `version` = `VERSION` дистрибутива).
- **Переводы строк** (если цель — git-репозиторий): `git ls-files --eol` по
  установленным путям не показывает расхождений между колонкой `attr/` и
  фактическим состоянием рабочего дерева (`w/`). Расхождение означает, что
  на следующем checkout байты поменяются и манифест разъедется. Лечится
  приведением байтов к конвенции (текст — LF, `*.ps1` — CRLF) и пересчётом
  sha в манифесте, а не правкой одного лишь `.gitattributes`.
- **Рендер агентов**: каждый разложенный agent definition завершается блоком
  «Дисциплина исполнения» и профилем модели по семейству резолвнутой модели
  (`core/install/layout.md` §4–5, `core/install/model-profiles.md`);
  отсутствие блоков или прозаические упоминания инструментов — признак
  незавершённого рендера.
- **Модель и усилие**: у каждого агента поле усилия соответствует колонке
  `effort` роли по карте моделей; ни у одного агента не стоит верхняя ступень
  (`max`) — она только ручная эскалация.
- **ro-allowlist**: у ролей `ro` в allowlist нет серверов, классифицированных
  `access: rw` в MCP-инвентаре (§1.1, layout §2).
- **Хук напоминания правил** (если ставился, §4.2/§5.1): `--check-map` печатает
  «все правила на месте»; `--dry-run` на пути из карты печатает строки правил;
  живость точки регистрации подтверждена зондом. Непройденная любая из трёх —
  хук считается **не поставленным** и идёт в отчёт как пропуск, а не как
  установка: наполовину живой хук хуже отсутствующего, потому что на него
  рассчитывают.
- **Проверки раскладки**: `CLAUDE.md` содержит **ровно** строку
  `See @AGENTS.md`; каталог `.claude/rules/` **не существует**; remote-серверы
  в `.mcp.json` несут `"type": "http"`.

## 11. Отчёт

Короткий итог пользователю:

- какой набор правил установлен (Rule Index);
- что **создано/изменено** (+ путь бэкапа);
- **MCP**: включено / исключено / не проверено (и почему);
- заполненные **плейсхолдеры** и оставшиеся `НЕ НАСТРОЕНО`;
- **манифест** записан (версия);
- **хук напоминания правил**: поставлен (сколько записей карты, подтверждена ли
  живость точки) или пропущен — и по какой причине: нет Python, нет карты у
  оверлея, точка молчит;
- оставшиеся **риски** и следующий шаг.
